# Where we are at

## Done
- Grilling on the Market Data Acquisition PRD complete. Outcome: `CONTEXT.md` glossary, ADR-0001 (no scheduler), ADR-0002 (DuckDB via cgo), Phase 1 spec `.scratch/market-acquisition/spec.md`, issues 01–08.
- **Ticket 01 — domain types and module skeleton.** Go module `github.com/agnos/agnoforge` with the hexagonal layout from the spec (`cmd/agnoforge`, `internal/domain`, `internal/app`, `internal/adapters/{binance,duckdb,httpapi}`; only `internal/domain` has real code). Domain covers Timeframe (13 fixed durations, rejects 1s/1w/1M), half-open Range with union/intersect/subtract and the slice helpers, DatasetID, Bar with exact `big.Rat` validation, Gap + GapStatus, the TradingCalendar port with a Continuous (24/7) implementation, and the four sentinel errors. Table-driven tests throughout; `internal/domain` imports stdlib only and `go.mod` still has zero dependencies.
- **Ticket 02 — Store port and DuckDB adapter.** `internal/app/ports.go` declares the `Store` port (plus `GapFilter`) in domain terms only; `go list -deps ./internal/app` is still stdlib + domain, and nothing there names a database. `internal/adapters/duckdb` implements it against DuckDB 1.5.5 (`github.com/duckdb/duckdb-go/v2`, the only direct dependency): one file, three tables (`bars` PK on the Dataset + open_time with `DECIMAL(20,8)` prices, `coverage`, `gaps` on a sequence), idempotent `INSERT OR REPLACE` upserts, coverage union-merged through `domain.MergeRanges`, half-open gap intersection, and Parquet export via DuckDB's own `COPY … TO`. 24 tests, all on `:memory:`, with a `TestMain` guard that fails the package if a run leaves a database or Parquet file on disk.

- **Ticket 03 — Provider port and Binance adapter.** `internal/app/ports.go` now declares `Provider` alongside `Store`, still in domain terms only (`go list -deps ./internal/app` remains stdlib + domain, and nothing there names Binance). `internal/adapters/binance` implements it over `GET /api/v3/klines`: the 13 canonical timeframes, `EarliestAvailable` from the oldest bar, a Continuous calendar, and a `Bars` iterator that clips the start up to the earliest available bar and the end down to the last fully closed one, pages 1000 at a time, and drops invalid bars with a `slog` warning. Failure handling is all in the adapter: five attempts with doubling backoff, `Retry-After` honoured on 429/418, 5xx and transport errors retried, every other 4xx permanent, and Binance code `-1121` surfaced as `domain.ErrUnknownSymbol` without a retry. A mutex token bucket (6000 weight/min, klines weight 2, continuous refill) is held per Provider and shared by every concurrent caller. Clock, sleep, logger and backoff base are injectable, so the 18 tests run on a fake clock against `httptest` with a `TestMain` that blocks every non-loopback host.
- **Ticket 04 — Backfill use case.** `internal/app` now runs Backfills: `app.New(store, providers, opts…)` builds a `Service` over the two ports, `StartBackfill` validates the Provider, the Timeframe and the Symbol, resolves the effective range (start clipped up to `EarliestAvailable`), registers the Backfill in an in-memory registry (one running per Dataset, second request → `domain.ErrBackfillRunning`) and returns the id and range immediately while a background goroutine on its own context acquires the pages. Each yielded page is upserted and only then has its Coverage extended, so Coverage never claims Bars a failed write did not store; a completed Backfill extends Coverage to the whole effective range, a failed or cancelled one keeps just what landed. `Backfill`, `CancelBackfill`, `Providers` and a `Wait` helper round out the API, and every terminal state runs the minimal `DetectGaps` (expected − present − ignored/unrecoverable, coalesced, open gaps replaced) over the landed range. 15 tests (18 cases with the terminal-state subtests) against a fake Provider and real in-memory DuckDB, all under `-race`; `go list -deps ./internal/app` is still stdlib + `internal/domain`.

- **Ticket 05 — gap detection and the Complete query.** `DetectGaps` is now the full rule: inside `r ∩ Coverage` only, expected (from the Provider's TradingCalendar) − present − the ranges of `ignored`/`unrecoverable` Gaps, one `open` Gap per run of consecutive missing expected open_times, `[firstMissing, lastMissing+tf)`. Contiguity is measured in the calendar's expected sequence, so a market-closed period is never a Gap and never breaks a run across it — Bars absent on either side of a closed weekend are one Gap. Before replacing the open Gaps in range, any Gap the range touches whose data the Dataset now holds in full is set `repaired` — `open` ones that were filled, and the `ignored`/`unrecoverable` ones ticket 06's Repair will fill — and repaired Gaps stop excluding anything. `IsComplete` answers the only question other services should ask: `Completeness{Complete, Gaps}`, true iff the range lies inside Coverage and no `open` Gap intersects it (touching ≠ intersecting), returning the intersecting open Gaps. 7 new tests (19 cases) against a fake Provider — now with a pluggable calendar, including a weekend-closing one — and real in-memory DuckDB, under `-race`; `internal/app` is still stdlib + `internal/domain`.

- **Ticket 06 — Repair and gap status changes.** `internal/app` now closes the operator loop: `Repair(gapID)` loads the Gap, starts a Backfill over exactly that Gap's range in that Gap's Dataset, and returns its status — inheriting the whole Backfill machinery, so `domain.ErrBackfillRunning` propagates for a busy Dataset and `domain.ErrNotFound` for a Gap that does not exist. It sets no status itself: the Backfill's terminal gap detection runs over the landed range, which is the Gap's range, so ticket 05's rule marks the Gap `repaired` on its own — an `ignored` or `unrecoverable` Gap whose data now exists included, by the same code path. `SetGapStatus(gapID, status, reason)` records an operator's judgement for `open`, `ignored` and `unrecoverable` only; `repaired` and any non-canonical status are refused with `app.ErrGapStatusNotSettable` (the HTTP 400 the next ticket needs, via `errors.Is`) and leave the Gap untouched, and the reason is stored as given, empty allowed. 9 new tests (15 cases) against the fake Provider and real in-memory DuckDB under `-race`, including the acceptance step that ignoring the only intersecting Gap makes `IsComplete` true; `internal/app` is still stdlib + `internal/domain` and `go.mod` is unchanged.

- **Ticket 07 — the HTTP API adapter.** `internal/adapters/httpapi` serves the whole Service over the standard library's pattern mux — ten routes, no router, `go.mod` unchanged: `GET /providers`, `POST /backfills` (202 with the id and the effective range, 409 for a Dataset already running, 400 for an unknown Provider/Symbol/Timeframe or a malformed range), `GET`/`DELETE /backfills/{id}`, the four Dataset queries (`coverage`, `complete`, `gaps`, `bars`), `PATCH /gaps/{id}` and `POST /gaps/{id}/repair`. Queries flag incompleteness and never refuse it: `…/bars` computes `IsComplete` first, sets `X-Complete` and `X-Gaps`, and only then streams DuckDB's own Parquet to the wire (`?format=json` returns the same Bars as decimal strings under the same headers). Every failure is `{"error":…}`, including the mux's own 404 and 405, which the package's one middleware — the same one that logs a line per request — rewrites. To keep the adapter off the Store, `Bars` joined the `Store` port and the Service gained thin `Coverage`/`Gaps`/`Gap`/`Bars`/`ExportParquet` reads. 26 tests over `httptest` against a fake Provider and real in-memory DuckDB, each route success *and* failure, the Parquet response read back by a second DuckDB through `read_parquet`, and a test asserting `go list -deps` names neither `duckdb` nor `binance`. Wire format is in `ASSUMPTIONS.md`; `internal/app` is still stdlib + `internal/domain`.

- **Ticket 08 — the CLI.** `cmd/agnoforge` is now the whole program and the only package that names a concrete adapter: `serve` reads `AGNOFORGE_DB_PATH` (default `agnoforge.duckdb`), `AGNOFORGE_LISTEN` (default `:8080`) and `BINANCE_BASE_URL` (through `binance.BaseURL()`), opens the DuckDB Store, builds the Binance Provider on a 30s client, hands both to `app.New`, serves `httpapi.New` over the listener, announces the bound address on stdout and shuts down gracefully on SIGINT/SIGTERM. `agnoforge data providers|backfill|status|cancel|gaps|repair|complete|query` are thin HTTP clients over `AGNOFORGE_URL` (default `http://localhost:8080`), one route each, argument parsing a `flag.FlagSet` per subcommand with the flags allowed to follow the positional arguments — no CLI framework, `go.mod` unchanged. `backfill -wait` polls to a terminal state; `complete` prints `complete: true|false` and exits 0 either way; `query` writes the Parquet body to `-o file` (or stdout for `-`) and prints the `X-Complete` verdict; any non-2xx is `error: <the service's message>` on stderr and exit 1, a usage error is exit 2 and no request. Everything is testable in-process because the entry point is `run(args, stdout, stderr, env)`: 18 tests (26 cases with the per-route subtests), including an end-to-end one that starts the real service on `127.0.0.1:0` over a DuckDB file in `t.TempDir()` and an httptest fake Binance serving 2,500 paged 1m klines, then drives `backfill -wait` → `complete` → `query` through the CLI, reads the exported Parquet back with a second DuckDB (2,500 rows), and reruns the Backfill to show nothing changes.

## Possible next
- Phase 1 is code-complete: tickets 01–08 are all `done`. What is left is the acceptance run against the real Provider — a person's call, not a test's.
- User may want to hand-run the spec's acceptance #1 for real: `go build ./cmd/agnoforge`, then `AGNOFORGE_DB_PATH=/tmp/agnoforge.duckdb ./agnoforge serve` in one shell and `./agnoforge data backfill binance BTCUSDT 1m 2024-01-01 2024-02-01 -wait` in another, expecting 44,640 bars, then `data complete …` and `data query … -o /tmp/jan.parquet`. That is the first time anything in this repo talks to `api.binance.com`.
- User may want to eyeball the ticket-08 section of `ASSUMPTIONS.md`: the exit codes (2 for usage, 1 for any non-2xx, 1 for a `-wait` that ends `failed`), the exact printed lines of `backfill`, `complete` and `query`, that `query`'s verdict goes to **stdout**, and that flags follow the positional arguments.
- User may want to eyeball the ticket-07 section of `ASSUMPTIONS.md`: every JSON field name is a choice the spec did not make, as are `DELETE /backfills/{id}` answering 202 with the status body, `application/vnd.apache.parquet` as the default content type, and an empty range being a 400.
- User may want to point `BINANCE_BASE_URL` at the real `api.binance.com` and hand-run a small backfill through the Service once there is a `cmd` entry point, to confirm paging and the token bucket behave against the live endpoint.
- User may want to eyeball the ticket-06 section of `ASSUMPTIONS.md`, in particular that an empty reason is accepted for every settable status, and that `Repair` returns the *effective* range (the Gap's range with its start clipped up to the Provider's earliest Bar — a no-op in practice, since a Gap always lies inside Coverage).
- User may want to eyeball the ticket-05 section of `ASSUMPTIONS.md`, in particular that a run of missing Bars spanning a closed period is **one** Gap.
- Reserved-for-later list lives at the bottom of the spec (Binance bulk-archive adapter, 1w/1M timeframes, persisted backfills).
