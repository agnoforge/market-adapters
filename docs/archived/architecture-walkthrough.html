agnoforge — Architecture Walkthrough

A ~2,900-line Go ports-and-adapters service (plus ~4,400 lines of tests) that backfills OHLCV bars from Binance into DuckDB and tells other services which ranges they can trust. Click any ▸ section to expand it; everything is collapsed by default so you can go as deep as you like. Companion to README.md (how to run) and CONTEXT.md (vocabulary).

Why a hexagon and not just "handler → repo"? concept

Because the two things most likely to change — which exchange and which database — sit outside the interfaces. This is ports & adapters (Cockburn): the use cases own the interfaces (app.Store, app.Provider) and the adapters implement them, so the dependency arrow points inward. The acceptance criterion in the tests spells it out: a second Provider needs no change under internal/app.

Why is the HTTP adapter "inbound" and the others "outbound"? concept

An inbound (driving) adapter calls the use cases; an outbound (driven) adapter is called by them through a port. httpapi holds a *app.Service and knows no Store; duckdb and binance never see the Service, they just satisfy an interface. Note there is no port for the inbound side — the Service's concrete methods are the API, which is fine because there is exactly one caller.

The one rule. domain ← app ← adapters ← cmd. Nothing imports "to the right". domain imports only the standard library.

2. File map and the import rule

Every real import between packages, as an arrow. Test files are omitted; they import one level in.

The adapters import app only for the port interfaces (and app.GapFilter), never for *app.Service. Each adapter pins that in one line: var _ app.Store = (*Store)(nil).
Isn't an adapter importing app a layering leak? subtle

No — it is the whole point. In Go the interface is declared where it is consumed, so app.Store lives beside the use cases that call it. The adapter imports that name to say "I satisfy it". What would be a leak is app importing duckdb; it does not, and the only place both names appear together is cmd/agnoforge/serve.go.

3. The core model

Three value types carry everything: a half-open Range, an exact-decimal Bar, and a Gap with a four-state lifecycle. A Backfill is not a domain type — it is a runtime record in app with its own lifecycle.

Why are prices string and not float64? design

Because the promise is "bars exactly as the provider reported them". A float would round 42000.12345678; a string passes through untouched, is stored as DECIMAL(20,8), and comes back cast to VARCHAR. Bar.Validate parses with math/big.Rat only to check low ≤ min(open,close) and high ≥ max(open,close), then throws the parsed value away.

Source: internal/domain/range.go — the algebra everything else leans on code
// Touching ranges do not overlap: [0,2) and [2,4) are adjacent, not shared.
func (r Range) Overlaps(other Range) bool {
    if r.IsEmpty() || other.IsEmpty() { return false }
    return r.Start.Before(other.End) && other.Start.Before(r.End)
}

// Union succeeds when the ranges overlap OR touch — so MergeRanges coalesces
// [0,2) and [2,4) into [0,4). This is what keeps Coverage as few rows as possible.
func (r Range) Union(other Range) (Range, bool)

// Subtract: 0 pieces (covered), 1 (edge trimmed), or 2 (hole punched).
func (r Range) Subtract(other Range) []Range

// IsComplete uses this: r ⊆ Coverage  ⇔  len(SubtractRanges([r], coverage)) == 0
func SubtractRanges(base, minus []Range) []Range

Two lifecycles

Why can an operator never set repaired? design

repaired is a fact about the data, not a decision: DetectGaps → settleGaps → isFilled checks every expected open_time is present and only then flips the status. Service.SetGapStatus refuses it with ErrGapStatusNotSettable (→ 400). The other three are judgements an operator is entitled to make and unmake.

Why is the Backfill registry a map and not a table? ponytail

backfill.go:114 — // ponytail: in-memory registry, persist when a Backfill must survive restart. ADR-0001 explains the ceiling: the whole Binance 1m history is ~4,700 requests, minutes not hours, and "resume" is just "run the same Backfill again" because Coverage + idempotent upserts already record what landed. A restart loses the status, never the bars.

4. Ports and their implementations

Two interfaces, both declared in internal/app/ports.go, each with one production implementation and one test double.

Why iter.Seq2 for pages and open_times rather than a slice? pattern

Streaming with back-pressure. A month of 1m bars is 44,640 rows; a year is half a million. The Provider yields one HTTP page at a time and the Backfill persists it before pulling the next, so memory is bounded by pageLimit (1000) and a cancel is honoured between pages. The error convention is uniform: a failure is yielded once, with a nil/zero value, and ends the sequence.

Why does the Provider clip the range itself, when StartBackfill already computed an effective range? subtle

Two callers, two clocks. StartBackfill clips so the recorded Coverage never claims instants no Provider could have served. binance.Bars clips again — "belt and braces" in the source — because the port contract says a forming bar is never yielded, whoever calls it. The test double fakeProvider relies on that contract living behind the port.

5. Use cases — which port methods each one touches

One struct, app.Service, spread over five files by use case. Numbers are call order.

Coverage is extended twice. ⑤ per page, only over bars already persisted, so Coverage never claims bars that are not there. ⑥ once at completion, over the whole effective range, so the instants the Provider had no bar for become Gaps instead of unknowns.
Source: backfill.go — the run loop code
for page, err := range p.Bars(ctx, ds.Symbol, ds.Timeframe, eff) {
    if err != nil { failure = err; cancelled = ctx.Err() != nil; break }
    if ctx.Err() != nil { cancelled = true; break }   // ← cancel honoured only between pages
    if err := s.store.UpsertBars(ctx, ds, page); err != nil { … }
    last := page[len(page)-1].OpenTime.UTC()
    // ⑤ Coverage only for a page that is already persisted
    s.store.ExtendCoverage(ctx, ds, domain.Range{Start: page[0].OpenTime.UTC(), End: last.Add(step)})
}
term := context.Background()                    // ← terminal work survives a cancel
if state == StateCompleted { s.store.ExtendCoverage(term, ds, eff) }   // ⑥
landed := eff
if state != StateCompleted { landed = domain.Range{Start: eff.Start, End: position.Add(step)} }
gaps, err := s.DetectGaps(term, ds, landed)    // ⑦ before State flips, so a Repair can't be undone by a stale run
How does DetectGaps turn "expected − present" into Gap records? design
  1. Widen r to the hull of every open Gap it intersects — ReplaceOpenGaps will delete those, so they must be re-detected in full.
  2. Settle: for every non-repaired Gap touching r, if isFilled → mark repaired; otherwise if ignored/unrecoverable → collect its range as "not expected".
  3. Walk each Coverage piece ∩ r: iterate calendar.Expected(piece, tf); an expected time that is neither present nor settled extends the current run, anything else flushes it as one Gap{Start: first, End: last+step}.
  4. Replace open Gaps in r with what was found, in one transaction.

Only Coverage is judged. A range never asked for is unknown, not missing.

Why is Repair only four lines? ADR-0001

Because a Repair is a Backfill over the Gap's range. Idempotent upserts + Coverage merge + terminal gap detection mean nothing extra is needed: when the bars land, ⑦ sees the Gap filled and flips it to repaired. ADR-0001 rejected a persistent job table on exactly this reasoning.

Why does GET …/bars set X-Complete/X-Gaps headers instead of refusing an incomplete range? design

"Serve, don't refuse." A backtester may want partial data knowingly. Completeness is computed before the first body byte so the headers are always present; the body then streams Parquet straight from DuckDB's COPY … TO. If the export fails after bytes went out, the only honest option left is to truncate and log — hence countingWriter.

Why the recorder wrapper around ResponseWriter? subtle

The stdlib mux writes its own plain-text 404 page not found and 405. The recorder intercepts WriteHeader for those two codes when no JSON content type was set, replaces the body with {"error":"not found"}, and swallows the mux's later Write. A handler's own 404 already carries JSON and passes through untouched.

Why hand-roll a token bucket instead of golang.org/x/time/rate? ponytail

bucket.go: "a mutex and two floats: the budget is per-process, so there is nothing here a library would do better." It also takes injected now/sleep, which is what lets the retry and rate-limit tests run on a fake clock with zero real waiting. The repo has exactly one external dependency (DuckDB) and this keeps it that way.

Why does shutdown wait for Backfills before closing the Store? subtle

A running Backfill's terminal work (⑥⑦) writes Coverage and Gaps on context.Background(). If the Store closed first those writes would fail and the Dataset would be left with Coverage but no Gap records — a silently incomplete range that IsComplete would call Complete. svc.Shutdown cancels each run and blocks on its done channel, which only closes after ⑦.

9. Tests — what gets swapped at each edge

~4,400 lines, go test -race ./..., six packages. No mocking library; every double is a hand-written struct that satisfies a port or a fake HTTP server.

Why is DuckDB not faked in app_test? practice

Because :memory: is fast, exact and has the real PRIMARY KEY — a fake Store would have to re-implement the upsert and the intersect predicate that the gap logic depends on, and bugs there are the ones worth catching. The Provider is the expensive, non-deterministic edge, so it is the one that gets a double. fakeProvider.onPage is the hook used to inspect the Store mid-Backfill and to make two Backfills race.

How do retry/rate-limit tests avoid real sleeping? practice

binance_test.clock only advances when something calls its Sleep, which records the duration and moves now. Inject it with WithClock(c.Now), WithSleep(c.Sleep); then assert on c.Sleeps() — e.g. [500ms, 1s, 2s, 4s] for four backoffs, or [7s] for a Retry-After: 7.

10. Check yourself

Quick quiz practice

Q1. A Backfill for [Jan 1, Feb 1) is cancelled after 3 pages. What does Coverage say afterwards, and does IsComplete(Jan) return true?

Coverage is the union of the three per-page extensions ⑤ (the final ⑥ over eff only runs on completed). DetectGaps ran over [eff.Start, position+step), so no Gaps exist inside what landed. IsComplete(Jan) is false: SubtractRanges([Jan], coverage) is non-empty because the rest of January was never covered — unknown, not a Gap.

Q2. An operator PATCHes a Gap to ignored, then someone runs POST /gaps/{id}/repair and the bars arrive. What is the Gap's status?

repaired. Repair is a Backfill over the Gap's range; its terminal DetectGaps → settleGaps checks every non-repaired Gap in range with isFilled, "whatever status it was in", and flips it. The operator's judgement is overridden by the data.

Q3. You add a Kraken adapter. Which packages change?

New internal/adapters/kraken (implements app.Provider, likely with its own TradingCalendar if not 24/7) and one line in cmd/agnoforge/serve.go: []app.Provider{provider, kraken}. Nothing under internal/app, domain, duckdb or httpapi — the URL already carries {provider} and GET /providers lists whatever the Service was built with.

Q4. Why does ReplaceOpenGaps use start_ms < ?end AND end_ms > ?start and not <= / >=?

Strict inequalities encode Range.Overlaps: touching ranges share no instant. A Gap ending exactly where the detected range starts must survive, otherwise re-detecting [Feb, Mar) would delete a January Gap it never looked at.
