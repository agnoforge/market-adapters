00 · Before architecture

Why does this exist?

A backtest replays months of price bars through a trading strategy. That takes minutes. A web request cannot wait minutes.

So Agnostix splits the work in two:

  1. When you press Run backtest, the server only writes down a job ticket — "run strategy X on symbol Y over this date range" — and answers immediately with a job id.
  2. A background worker picks tickets up one at a time, does the heavy computation, and keeps updating the ticket: how far along it is, and eventually whether it finished, failed, or was cancelled.

Meanwhile the UI just polls the ticket. It can also pause, resume, or delete a job while it runs.

The problem with the naive version. Sprinkle a status string column around and every part of the code starts flipping it: the HTTP handler sets "running", the worker sets "completed", a crash leaves a job "running" forever, and nothing stops a delete handler from marking a finished job "pending" again. Job lifecycle bugs are concurrency bugs — two actors (web server and worker) mutate the same row.
How do we arrange this so that the database, the web framework, and the compute engine are all replaceable — without their details leaking into the one part that decides which lifecycle moves are legal?

This page teaches the Job context: async job orchestration only. The backtest computation itself (engine, strategies, trades) belongs to the Trading context — here it is just "the heavy work the job wraps".

The one running example

POST /api/v1/backtests
{ "strategy_name": "SMACross", "symbol": "EURUSD",
  "start": "2024-01-01", "end": "2024-02-01",
  "initial_balance": 10000.0 }
→ { "job_id": "7f3a…" }          # we follow job 7f3a… on every page

01 · The core

Start with the domain core

What does the Job context fundamentally talk about? One thing: the lifecycle of a job.

ConceptThe core is the innermost ring: the vocabulary and rules of the business, written with no knowledge of databases, HTTP, or async runtimes. Everything else will be drawn around it.
AgnostixLives in crates/domain/src/backtest_job_state.rs. Its imports are other domain modules (Symbol, Timeframe, RangeUtc, Money) plus the time crate — no ports, no SQL, no tokio.

02 · Core · BacktestJobState

Six states — a job's whole life

Job 7f3a… is born Pending. Everything after that is a legal move or a rejected one.

Pending ──start()──▶ Running ──complete()──▶ Completed ✓ terminal │ │ ⇅ pause()/resume() │ ├──fail()───────────▶ Failed ✓ terminal │ └─(Paused can also complete/fail) ├──cancel()──▶ Cancelled ✓ terminal └──fail()────▶ Failed # e.g. validation before start Completed.start() → Err(InvalidSourceState) # the type system says no

Why an enum and not a status column?

Because each state carries different data. RunningData has started_at, total_bars, processed_bars and live stats; CompletedData has completed_at and final JobStats; CancelledData has only cancelled_at. With a status string plus 20 nullable columns, "a Pending job with a completed_at" is representable. With this enum it is not.

AgnostixTerminal states are exactly Completed | Failed | Cancelled (is_terminal()). state_name() renders the lowercase strings "pending" … "cancelled" used for persistence and the HTTP API.
Honest note. The module's doc-comment state diagram omits Paused; the code has it (pause() / resume(), and complete()/fail() accept Paused too). The code wins.
Show me the code — one transition
pub fn start(self, total_bars: u32, now: OffsetDateTime)
    -> Result<(Self, JobStateEvent), TransitionError> {
    match self {
        Self::Pending(data) => {
            let event = JobStateEvent::JobStarted { job_id: …, started_at: now, total_bars };
            Ok((Self::Running(RunningData { config: data.config, started_at: now,
                total_bars, processed_bars: 0, progress_percentage: 0.0, … }), event))
        }
        other => Err(TransitionError::InvalidSourceState {
            from: other.state_name(), to: "running" }),
    }
}

03 · Core · JobStateEvent / TransitionError

Every move returns two things

Each transition consumes the old state and returns (new state, event) — or an error. Nothing mutates in place.

state.start(59_040, now) → Ok((Running{…}, JobStarted{job_id: 7f3a…, total_bars: 59_040})) state.update_progress(ProgressUpdate{ processed_bars: 29_520, progress_percentage: 50.0, … }) → Ok((Running{…}, ProgressUpdated{processed_bars: 29_520, progress_percentage: 50.0}))

Why events?

The doc comment says it directly: audit logging, event sourcing, side effects (notifications, metrics). Today the events are produced and returned; nothing in this context subscribes to them yet — they document what happened, and callers may ignore them (let (_state, _event) = …).

The two failure shapes

VariantMeaningDisplay
InvalidSourceState { from, to }You asked for a move the machine forbids"Invalid state transition: completed -> running"
PreconditionFailed { reason }Move exists but a precondition was not met"Transition precondition failed: …"
AgnostixProgressUpdate is the input record for the self-transition update_progress() — Running → Running. Its optional total_bars lets the worker claim a job before counting bars, then fill the total in later (this is exactly what the worker does).

05 · Application · writes

Create, Pause, Resume, Delete

The four moves a user can make on a job, from the outside.

CreateBacktestJob

What it is: turns a request ("SMACross, EURUSD, Jan 2024, $10,000") into a persisted Pending job ticket. When it runs: the user presses Run backtest.

What happens:

  1. Generate a fresh BacktestJobId (UUID v4).
  2. Take symbol + timeframe from the first subscription; no subscriptions → Error::Validation("At least one subscription is required").
  3. Serialize strategy params to a JSON string.
  4. Build a BacktestJob with status: Pending, zeroed progress.
  5. Persist it and answer with the job id.

Required dependencies — via ports: job repository. Response payload:

create_job::Output { job_id: BacktestJobId }

PauseBacktestJob / ResumeBacktestJob

What they are: the two halves of one freeze/unfreeze lifecycle:

1. check get_state(7f3a…) → must be Running (pause) / Paused (resume) 2. poke job_control.pause() → flips an in-memory flag the engine loop watches 3. persist transition_to_paused() → domain pause(): Running → Paused, JobPaused event

Order matters and the code comments say why: "Pause in-memory execution first; then persist paused status." Wrong state → Error::Validation("Job … is not running") (or "… is not paused").

Required dependencies — via ports: the state-machine job repository and a job-control handle. Two different needs — remember that for the ports chapter.

DeleteBacktestJob

What it is: delete a job and everything it produced — and, if it is currently executing, get it to stop first.

  1. Load the job; missing → NotFound.
  2. If status is Running | Paused — or the control handle says this process is actively executing it — request cancellation (best-effort, result ignored).
  3. Wait up to 10 seconds, polling is_active() every 100 ms, for the in-flight run to let go.
  4. job_repo.delete() — removes the job and associated trades/progress.
Show me the code — PauseBacktestJob
impl PauseBacktestJobPort for PauseBacktestJob {
    async fn execute(&self, input: pause_job::Input) -> Result<(), Error> {
        let state = self.job_state_repo.get_state(&input.job_id).await?
            .ok_or_else(|| Error::NotFound(…))?;
        if state.as_running().is_none() {
            return Err(Error::Validation(format!("Job {} is not running", …)));
        }
        // Pause in-memory execution first; then persist paused status.
        self.job_control.pause(&input.job_id).await?;
        self.job_state_repo.transition_to_paused(&input.job_id).await?;
        Ok(())
    }
}

07 · Why ports exist

The application needs help

Look at the diagram: two unnamed sockets just appeared under the use cases. The use cases have needs they cannot meet themselves.

CreateBacktestJob must keep job 7f3a… somewhere that survives a restart. Should it know DuckDB SQL, connection pools, spawn_blocking? No. It should say "persist this job" in its own vocabulary.
PauseBacktestJob must interrupt a compute loop that is running right now, in another task. Should it know about atomic flags inside the backtest engine? No. It should say "pause job 7f3a…" and let someone else know how.
ConceptA port is a trait owned by the inner layer, written in the inner layer's vocabulary. The concrete technology implements the trait. That flip — the outer thing depends on the inner thing's contract — is dependency inversion, and it is the whole trick of hexagonal architecture.

In crates/ports/src/ the Job context owns outbound ports (what the app needs) and inbound ports (what the app offers). Next: the three outbound ports that define this context's edges.

The doc comment is explicit: legacy is kept for backward compatibility, new code should use the state-machine trait. Today Create/Get/List/Delete/GetEvents use cases still ride the legacy trait; Pause/Resume and the worker use the state-machine trait. One concrete adapter implements both, so they cannot drift in storage — only in API.

09 · Outbound port

BacktestJobControl

"Poke the run that is happening right now." Not persistence — live process control.

//! Outbound port for controlling in-flight backtest jobs (pause/resume).
#[async_trait]
pub trait BacktestJobControl: Send + Sync {
    async fn pause(&self, job_id: &BacktestJobId) -> Result<(), Error>;
    async fn resume(&self, job_id: &BacktestJobId) -> Result<(), Error>;
    /// Best-effort request to stop an in-flight job (used by delete).
    async fn cancel(&self, job_id: &BacktestJobId) -> Result<(), Error>;
    /// Returns true if this process currently controls the job execution.
    async fn is_active(&self, job_id: &BacktestJobId) -> bool;
}

File: crates/ports/src/outbound/backtest_job_control.rs (verbatim, complete)

Why is this a separate port from the repository?

Because they answer different questions with different lifetimes. The repository answers "what is the durable truth about job 7f3a…?" — valid across restarts and processes. Job control answers "is this process executing it right now, and can I signal that execution?" — meaningful only while the run is in flight. Merging them would smuggle process-local state into a persistence contract.

Note cancel() is documented as best-effort and exists for delete — there is no user-facing "cancel" endpoint; the doc comment tells you the intended caller.

async fn transition_to_running(&self, id: &BacktestJobId, total_bars: u32) -> … {
    let state = self.get_state(id).await?.ok_or_else(|| Error::NotFound(…))?;
    let (new_state, event) = state.start(total_bars, OffsetDateTime::now_utc())
        .map_err(|e| Error::Validation(e.to_string()))?;   // ← domain rule runs here
    self.save_state(&new_state).await?;
    Ok((new_state, event))
}

12 · Outbound adapter

BacktestJobController — the in-memory switchboard

Implements BacktestJobControl with nothing but a map of flags. No database anywhere.

pub struct BacktestJobController {
    controls: RwLock<HashMap<String, Arc<BacktestControl>>>,
}
// worker calls register(job_id, control) when a run starts, unregister() when it ends

async fn pause(&self, job_id: &BacktestJobId) -> Result<(), Error> {
    let control = self.controls.read().await.get(job_id.as_str()).cloned()
        .ok_or_else(|| Error::Validation(format!(
            "Job {} is not currently running on this server", job_id.as_str())))?;
    control.request_pause();
    Ok(())
}

File: crates/app/src/backtest_job_control.rs

How the poke lands: BacktestControl is a set of flags the engine's bar loop checks between bars — paused means "spin and wait", cancelled means "stop and return". is_active() is just "is the job in the map?", which is why delete can poll it to know when the run has let go.

Honest note ×2. (1) This adapter lives in crates/app — the composition-root crate — not in an adapters/ crate like its DuckDB siblings. (2) It imports BacktestControl from adapters_outbound_trading_engine: an adapter depending on another adapter's type. Both are pragmatic shortcuts the crate layout makes visible.

15 · The background worker

BacktestWorker — the second driver

Nobody calls it. It wakes itself up: an endless tokio loop that polls for Pending jobs every second and runs them.

pub async fn run(&self) {
    while !self.shutdown.load(Ordering::Relaxed) {
        match self.poll_and_process_job().await {
            Ok(true)  => continue,                  // processed one — look again now
            Ok(false) => sleep(poll_interval).await, // queue empty — 1s nap
            Err(e)    => { tracing::error!(…); sleep(poll_interval).await }
        }
    }
}

File: crates/app/src/backtest_worker.rs

One job, start to finish

  1. fetch_next_pending_state() — FIFO claim from the repository-as-queue.
  2. transition_to_running(id, 0) immediately, before loading bars — "so the UI doesn't sit in Pending while bars load". Total bars is filled in later via ProgressUpdate { total_bars: Some(n) }.
  3. Load bars. Zero bars, too many bars (cap max_bars_per_job, default 1,000,000), or a load error → transition_to_failed(...) with a human message. Jobs never stick in Pending.
  4. Register a BacktestControl with the BacktestJobController — now pause/resume/cancel can reach this run.
  5. Run the engine in spawn_blocking; a side task calls transition_update_progress every ~100 bars (progress_batch_size), skipping while paused.
  6. Afterwards: cancelled → transition_to_failed("Cancelled by user"), skip persistence. Deleted mid-run (get_state = None) → skip persistence. Otherwise persist trades, hourly-thinned progress points, order events, UI events — then transition_to_completed(stats).
  7. Unregister the control handle. Errors anywhere → transition_to_failed(e.to_string()).
Honest note — the big asymmetry of this context. The worker is a driving actor, but it does not enter through inbound ports or use cases. It calls BacktestJobStateRepository (an outbound port) and the other repositories directly, and it lives in crates/app beside the composition root, not in an adapters crate. Consequence: job-execution policy (claim early, fail on empty bars, cancel-means-failed) lives in the worker, not in a use case — a trade-off the module docs embrace by pushing all legality checks into the domain state machine, which the worker cannot bypass.
Honest note — the unused state. Nothing calls the domain's cancel() (Pending → Cancelled): transition_to_cancelled is implemented by the DuckDB adapter but has no caller in use cases or worker. A cancelled running job is persisted as Failed("Cancelled by user"), and the legacy conversion even maps Cancelled → Failed status. The Cancelled state is real in the domain, and reachable through the repository API, but today's flows route cancellation through delete + fail.

Now derive the rule

Every arrow you saw pointed the same way once you follow compile-time dependencies:

domain ← ports ← usecases ← adapters ← app (root)
# runtime calls flow in; source dependencies point in too — that is the dependency rule
Where does "retry failed jobs automatically" go?
The legality of Failed → Pending would be a new domain transition; the policy (when, how many retries) is worker or use-case logic; persistence needs a transition_to_* on the state repository port + adapter. Domain first, then outward.
Where does "run jobs on two servers" go?
The claim step (fetch_next_pending_state + transition_to_running) must become atomic across processes — an adapter/port concern. BacktestJobControl.is_active() already anticipates this: it answers for this process only, and its error says "not currently running on this server".
Where does a "cancel" button (without delete) go?
Route in the HTTP adapter → new CancelBacktestJobPort inbound port → use case calling job_control.cancel() + the already-implemented transition_to_cancelled. The domain and adapter are ready; only the middle is missing.
Where does the actual backtest math go?
Not here. Engine, strategies, trades, stats are the Trading context (adapters/outbound_trading_engine, run_backtest_uc, …). The Job context only wraps that work in a durable lifecycle.
Where does a WebSocket progress push go?
A new inbound adapter subscribing to job state — or a real consumer for JobStateEvent, which is emitted on every transition today and dropped. The events were designed for exactly this.

19 · Runtime · the repair paths

Pause it, resume it, kill it

The same job, but now the user interferes mid-run. Watch the second port earn its keep.

  1. Pause requestedPOST /api/v1/backtests/7f3a…/pause → PauseBacktestJobPort::execute.
  2. Guard: is it Running?get_state(7f3a…); as_running() is None → Error::Validation("Job 7f3a… is not running"). It is Running — continue.
  3. Poke the live run firstjob_control.pause() → BacktestJobController finds 7f3a… in its map → request_pause(). The engine loop sees the flag between bars and idles; the progress task skips reporting while paused.
  4. Then persist: Running → Pausedtransition_to_paused — domain pause() keeps all progress fields, emits JobPaused. The UI now shows "paused" at 50%.
  5. Resume mirrors itPOST …/resume: guard as_paused(), request_resume() to wake the loop, then transition_to_resumed — domain resume(): Paused → Running, JobResumed.
  6. User gives up: deleteDELETE /api/v1/backtests/7f3a… — remember, there is no cancel route; delete is cancel.
  7. Best-effort stop, then waitStatus is Running (or is_active()) → job_control.cancel() sets the cancel flag; use case polls is_active() every 100 ms, up to 10 s, for the run to let go.
  8. Worker noticesEngine returns; control.is_cancelled() → skip persisting results, transition_to_failed(7f3a…, "Cancelled by user"), unregister. (A NotFound here is fine — the job may already be gone.)
  9. Row and offspring deletedjob_repo.delete(7f3a…) removes the job and its associated data (trades, progress). The ticket never existed — except in the logs.
Why "Failed" and not "Cancelled"? Covered on the worker page: today's cancel path is delete-driven and records Failed("Cancelled by user"); the domain's Cancelled state (Pending → Cancelled) has machinery but no caller.

20 · Confidence

How the architecture makes testing easier

The seams you just learned are exactly where the tests sit — and where they are honestly missing.

LayerHow it is testedReal / fake
Domain state machine20 unit tests in backtest_job_state.rs's mod tests: every legal transition, every rejected one (test_cannot_cancel_running_job, test_terminal_states_cannot_start/cancel/complete…), progress updates, legacy conversionsAll real — pure functions, nothing to fake, no async, no DB
Worker (pure part)Unit tests on build_ui_backtest_events in backtest_worker.rs — order-lifecycle → UI-event mapping (SL/TP set, TP hit, no cancel events)Real — the function takes plain domain values
Use casesNone today. The seam is ready: each takes Arc<dyn Trait>, so a test would hand in fake repos/control and assert e.g. "pause on a Pending job → Validation error, control never poked"Would be all fakes
DuckDB adapterNo dedicated tests in the module; exercised through the running app. Its transition methods stay thin by delegating legality to the (heavily tested) domainWould need a real temp DB
HTTP adapter / worker loopNo tests; both are thin translators around tested seams (routes → ports; loop → repo + engine)—
The design lesson: the tests are densest exactly where the rules are — the core — and the untested outer code is the code that cannot break the lifecycle, because every write path funnels through BacktestJobState's transitions.
