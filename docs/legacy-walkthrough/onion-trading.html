00 · Before architecture

You wrote a trading strategy. Will it make money?

Agnostix stores years of price bars. The Trading context answers two questions about a strategy: what would it have done on past data (a backtest), and what does it do right now on live prices (live trading).

  1. A strategy is a small piece of decision logic: "when the fast average crosses above the slow one, buy".
  2. A backtest replays historical bars through that logic, simulating fills, stop-losses, take-profits and commissions, and reports the equity curve and every trade.
  3. Live trading runs the same logic against a live price feed and sends its orders to an execution venue (today: a simulated paper broker).
The problem with the naive version. Put strategy logic, price loading, fill simulation, broker calls and SQL in one file and you can never answer: does the backtest and the live session run the same strategy code? Can I test the fill logic without a database? Can I swap the paper broker for a real one without touching the strategy?
How do we arrange this so that the market-data store, the execution venue and the strategies themselves are replaceable — without their details leaking into the parts that decide what a trade means?

The one running example

Used on every page of this explainer:

strategy   "SMACross"   (fast SMA 13 / slow SMA 21 on H1, close price)
symbol     EURUSD · base timeframe M1
range      2024-01-02 → 2024-01-31
balance    $10,000 · lot_size 0.1 · SL 50 pips · TP 50 pips

Scope note: this page covers backtest execution and live trading. Async job orchestration (queuing, progress %, pause/resume) belongs to the Job context and is out of scope here.

01 · The core

Start with the domain core

What does the Trading context fundamentally talk about? Orders, positions, ticks, and backtest results — as plain Rust data, with no I/O anywhere near them.

ConceptThe innermost ring holds the vocabulary of the business. It depends on nothing below it — no database, no HTTP, no async runtime — so every other layer can speak its language without dragging in machinery.
AgnostixLives in crates/domain/src/trading.rs and crates/domain/src/tick.rs. The whole domain crate has exactly one dependency: the time crate for timestamps (verified in crates/domain/Cargo.toml).

Don't read it as a pile of entities — sort it into kinds

Almost nothing in this core is a classic "entity with behaviour". It is mostly typed facts and a small vocabulary:

KindMembersIn Rust, this is…
Records (typed facts)Order, Execution, Position, TradeSummary, EquityPoint, OrderLifecycleEvent, BacktestResult, BacktestStatsplain structs with public fields, Clone
Values / enums (the vocabulary)Side, PositionSide, OrderType, OrderStatus, PositionStatus, TimeInForce, OrderEventType, SlTpTrigger; ids OrderId, PositionId, StrategyId; aliases Money, Volume (= f64)enums and newtype tuples
Config / policyBacktestConfig, SubscriptionSpec, TickSimulationConfigstructs the caller fills in; TickSimulationConfig has presets (forex(), crypto(), stock())
Pure rulesTick::mid(), Tick::spread(); the bid/ask execution rules documented on Ticksmall deterministic functions

A Position has invariants (it opens, accumulates PnL, closes once) but its lifecycle is driven from outside by the engine — it is a record plus status fields, not an aggregate with methods. The code is honest about that.

What it knows
What an order, position, tick, and backtest result are; the legal values of side/status/order-type; simulated-tick configuration.
What it must NOT know
Where bars come from, how fills happen, what DuckDB or Axum are, which strategies exist.
Who calls it
Every outer ring: use cases, ports, engines, repositories, HTTP handlers.
What it calls
Only std and the time crate.

02 · Core · Order & Position

Order & Position — intent, then exposure

An Order is what a strategy asks for. A Position is what it is holding as a result. They are two halves of one lifecycle.

SMACross sees fast SMA cross above slow SMA on EURUSD H1 → Order { side: Buy, order_type: Market, volume: 10_000, sl: 1.0850, tp: 1.0950 } ✓ placed → Position { side: Long, avg_price: 1.0900, status: Open, realized_pnl: 0.0 } ✓ opened …price hits take-profit… → Position { status: Closed, realized_pnl: +50.0, close_time: Some(…) } ✓ closed

Why two types?

One buy order can open a position; a later close can be partial (ClosePosition { volume: Option<Volume> } in the execution port). Keeping "what was requested" (Order, with its OrderStatus) separate from "what is held" (Position, with PositionStatus and running realized_pnl) makes both auditable.

Agnostixcrates/domain/src/trading.rs. Order carries stop_loss / take_profit / max_drawdown_price as Option<f64>; Position tracks avg_price, open_time, close_time, realized_pnl. Every executed fill is an Execution { order_id, ts, price, volume, commission }.

03 · Core · Tick

Tick — one price moment, with a spread

A Tick is a single bid/ask quote at one instant. Backtests do not trade on bars directly — they generate simulated ticks inside each bar, so fills, stop-losses and take-profits trigger at realistic intra-bar prices.

EURUSD M1 bar 09:00 O 1.0900 H 1.0910 L 1.0895 C 1.0905 → 60 simulated ticks/bar (TickSimulationConfig::forex(), 1-pip base spread) tick 09:00:07 { bid: 1.09031, ask: 1.09041 } ✓ buy fills at ask tick 09:00:31 { bid: 1.08999, ask: 1.09009 } SL check runs on every tick

The execution rules live here

The doc comment on Tick pins the four rules: open a BUY at ask, open a SELL at bid, close a BUY at bid, close a SELL at ask. SlTpTrigger names the three outcomes of a stop-loss/take-profit check: None, StopLoss, TakeProfit.

Agnostixcrates/domain/src/tick.rs. Tick::mid() and Tick::spread() are the only methods. TickSimulationConfig is policy: ticks_per_bar (default 60), base_spread, spread_variation, optional seed for reproducible runs, with forex() / crypto() / stock() presets. The generator that turns a bar into ticks is not here — it is adapter code (tick_simulation.rs in the backtest engine).

04 · Core · BacktestConfig → BacktestResult

BacktestConfig → BacktestResult — the question and the answer

A backtest is a pure question: given this config, what happens? The core defines both the question and the shape of the answer.

BacktestConfig { strategy_id: "SMACross", range: Jan 2024, initial_balance: 10_000.0, subscriptions: [ EURUSD @ M1 ] } │ (engine replays every bar as ticks) ▼ BacktestResult { equity_curve: [ EquityPoint { ts, equity } … one per bar ] ✓ trades: [ TradeSummary … one per closed position ] ✓ stats: BacktestStats { net_profit, max_drawdown, win_rate, … } order_events: [ OrderLifecycleEvent … open / modify / close ] ✓ full audit trail }

Why a separate event log?

TradeSummary only exists once a position has closed. OrderLifecycleEvent records every Open, Modify (SL/TP change) and Close as it happens (OrderEventType), so the UI can replay a run step by step. Its doc comment states the seam explicitly: these are engine-level events without a job_id; the Job context's worker later maps them to BacktestOrderEvent for persistence.

Agnostixcrates/domain/src/trading.rs. Persistence-shaped cousins also live here: BacktestTrade, BacktestEvent (+ MetaTrader-style BacktestEventType: BUY, SELL, BUY_STOP, …) and BacktestOrderEvent — the row types the repositories store.

05 · The next layer

Use cases — what can the Trading context do?

The core was the nouns. These are the verbs. Look at the diagram: a new box has appeared around the old one — the core did not move.

ConceptA use case is one thing a caller can ask the system to do, written entirely in domain vocabulary. It orchestrates; it never does I/O itself.

The Trading context has exactly three verbs, one file each in crates/usecases/src/:

  1. RunBacktest (run_backtest_uc.rs) — replay history through a strategy, return a BacktestResult.
  2. StartLiveTrading (start_live_trading_uc.rs) — spin up a live session for a strategy, return a session_id.
  3. StopLiveTrading (stop_live_trading_uc.rs) — stop a running session by id.

Start and Stop are two halves of one lifecycle, connected by a shared companion that also lives in the use-case layer: LiveSessionManager, an in-memory RwLock<HashMap<SessionId, LiveSession>> of running sessions.

start ──▶ session_id "3f2a…" stored in LiveSessionManager ✓ running …ticks flow, strategy trades… stop("3f2a…") ──▶ handle.stop() session removed ✓ stopped
AgnostixHonest note. The neighbouring backtest_jobs_uc.rs (create/pause/resume/delete job, progress) is the Job context — orchestration around backtests, not backtesting itself. Out of scope here.

06 · Use case

RunBacktest — replay history through a strategy

One question in, one answer out: config in domain terms → BacktestResult.

What is it
The synchronous backtest verb. Loads everything the engine needs, then hands over.
When does it run
When a caller invokes RunBacktestPort::execute(input) — today that caller is POST /api/v1/backtests/sync.
What happens
  1. Ask the strategy registry to build the named strategy ("SMACross") with its params; unknown name → Error::NotFound.
  2. Build SubscriptionSpecs — always on M1 as the base timeframe.
  3. Load M1 bars plus M5/M15/M30/H1/H4/D1 series for each subscription via BarRepository::fetch_range.
  4. Assemble BacktestConfig and an empty IndicatorDataBundle (indicators are computed on demand).
  5. Call TradingEnginePort::run_backtest(…) and wrap the result.
Required dependencies — via ports
TradingEnginePort, BarRepository, ExecutionVenue, StrategyRegistryPort
Response payload
dto::Output { result: BacktestResult }
Agnostixcrates/usecases/src/run_backtest_uc.rs — pub struct RunBacktest<E: ?Sized>, generic over the engine, implementing the inbound RunBacktestPort.
Architecture details

    bars: Arc<dyn BarRepository>,
    exec_venue: Arc<dyn ExecutionVenue>,
    strategy_registry: Arc<dyn StrategyRegistryPort>,

The M1 rule is a comment in the source: "Backtests always run on M1 as the base timeframe." Higher timeframes are loaded so strategies can call ctx.Close(H1, 1) or ctx.SMA(H1, 13, price_close, 1).

07 · Use case

StartLiveTrading — put a strategy on live prices

Same strategy code as the backtest, different data source: a live feed instead of stored history.

What is it
Creates a live session: builds the strategy, starts the live engine, records the session.
When does it run
When a caller invokes StartLiveTradingPort::execute(input).
What happens
  1. Validate + create the strategy via StrategyRegistryPort::create.
  2. Build subscriptions (live keeps the caller's timeframe — no M1 forcing here).
  3. Generate a session_id (UUID v4).
  4. Call LiveTradingEnginePort::start_session(config, strategy, exec_venue) → get a LiveSessionHandle.
  5. Store LiveSession { id, strategy_id, subscriptions, started_at, handle } in LiveSessionManager.
Required dependencies — via ports
LiveTradingEnginePort, StrategyRegistryPort, ExecutionVenue + shared LiveSessionManager
Response payload
dto::Output { session_id: String }
Agnostixcrates/usecases/src/start_live_trading_uc.rs. Default balance when none given: 10_000.0.
Architecture details
let config = LiveTradingConfig {
    session_id: session_id.clone(),
    strategy_id: StrategyId(input.strategy_name.clone()),
    initial_balance: input.initial_balance.unwrap_or(10_000.0),

};

    .start_session(config, strategy, self.exec_venue.clone())

The handle wraps a tokio oneshot::Sender<()> — the only way to reach into the running session, and only to stop it.

08 · Use case

StopLiveTrading — the other half of the lifecycle

Eleven lines of logic: find the session, send the stop signal, remove the record.

What is it
Stops one live session by id.
What happens
LiveSessionManager::stop_session(id) removes the session and calls handle.stop(), which fires the oneshot channel the engine's loop is listening on. Unknown id → Error::NotFound; a dead channel → Error::Internal.
Required dependencies
Only the shared LiveSessionManager — no ports at all.
Response payload
dto::Output { session_id, stopped: true }
Agnostixcrates/usecases/src/stop_live_trading_uc.rs. Note the asymmetry: stopping never touches the engine port — the handle captured at start time is the whole control surface.
Show me the code
impl StopLiveTradingPort for StopLiveTrading {
    async fn execute(&self, input: dto::Input) -> Result<dto::Output, Error> {
        self.session_manager.stop_session(&input.session_id).await?;
        Ok(dto::Output { session_id: input.session_id, stopped: true })
    }
}

09 · Why ports exist

The use cases need help

Four dashed sockets just appeared on the diagram. Each is an honest question.

RunBacktest needs a strategy called "SMACross". Should it know which strategies exist and how they are built? No. It asks a registry for a strategy by name.
RunBacktest needs the replay simulated; StartLiveTrading needs a live loop spawned. Should they know how ticks are simulated or how tokio tasks work? No. They ask an engine to run.
A live strategy says "buy 10,000 EURUSD". Should the use-case layer know whether that hits a paper simulator or a real broker? No. It hands the order to an execution venue.
Bars must be loaded; trades and events must be saved. Should anything inner know SQL? No. They talk to repositories.
ConceptA port is a contract owned by the inner layer, written in its vocabulary. The application defines what it needs; outer code implements it. That inversion — dependencies point inward — is the whole trick of the hexagon.

In this codebase ports are Rust traits in their own crate, crates/ports/src/, split into inbound/ (ways to drive the app) and outbound/ (things the app needs).

12 · Outbound port

StrategyRegistryPort & the Strategy trait

Strategies are plug-ins. The application asks for one by name; what it gets back is anything that speaks the Strategy trait.

// ports/src/outbound/strategy.rs — verbatim
pub trait StrategyRegistryPort: Send + Sync {
    fn create(&self, name: &str, params: &StrategyParams) -> Option<Box<dyn Strategy>>;
}

pub trait Strategy: Send + 'static {
    fn config(&self) -> StrategyConfig;
    fn on_init(&mut self, _ctx: &mut Ctx<'_>) {}
    fn on_deinit(&mut self, _ctx: &mut Ctx<'_>) {}
    fn on_bar(&mut self, _ctx: &mut Ctx<'_>, _sub: SubscriptionId) {}
    fn on_tick(&mut self, _ctx: &mut Ctx<'_>, _sub: SubscriptionId) {}
}

The same file defines the strategy author's world, deliberately MetaTrader-flavoured:

  • Ctx — everything a callback may touch: account, series access (ctx.Close(H1, 1)), indicators (ctx.SMA(tf, len, price_close, shift)), the current tick (bid()/ask()), and is_bar_open(tf).
  • TradeAction — the only way a strategy trades: it pushes Open { sub, side, volume, sl, tp, … }, Close or Modify into ctx.actions; helpers ctx.buy(…) / ctx.sell(…) / ctx.close_position(…) do the pushing. The strategy never executes anything itself.
  • StrategyParams = BTreeMap<String, String> — untyped params parsed by each strategy.
AgnostixFile: crates/ports/src/outbound/strategy.rs. The engine calls on_tick for every simulated/live tick; the doc comment on on_bar says the backtest engine no longer calls it as a separate phase — bar logic gates itself with ctx.is_bar_open(tf) inside on_tick.

15 · Outbound adapter

BacktestEngine — implements TradingEnginePort

The replay machine. Takes pre-loaded bars, explodes each into ~60 simulated ticks, feeds every tick to the strategy, and simulates every fill itself.

Tech detailHow the adapter handles it
Intra-bar prices don't exist in stored datagenerate_ticks_from_bar(bar, &TickSimulationConfig::forex()) in tick_simulation.rs synthesizes them
Which price fills an orderget_entry_price / get_exit_price apply the bid/ask rules from domain::tick
Stop-loss / take-profitcheck_sl_tp_trigger on every tick → SlTpTrigger::{StopLoss, TakeProfit, None}
Strategy tradescollects TradeActions pushed during on_tick, applies Open/Close/Modify to its own in-memory positions, assigns PositionIds, records OrderLifecycleEvents
Accountingtracks balance, equity, peak equity, max drawdown, margin stop-out (default 50%), leverage (default 100) — one EquityPoint per bar
AgnostixHonest note. The trait signature hands the engine an exec_venue, but the implementation names the parameter _exec_venue and never calls it — backtest fills are simulated inside the engine for speed and determinism. Only the live engine actually routes trades through ExecutionVenue. The symmetry is in the port, not (yet) in this adapter.
AgnostixCrate: crates/adapters/outbound_trading_engine/ (lib.rs ~2,560 lines + tick_simulation.rs). A second entry point, run_backtest_with_progress_counter, exists for the Job context's worker (progress + pause/cancel control) — same core loop.

impl TradingEnginePort for BacktestEngine {
    fn run_backtest(&self, config, subs, indicator_data, params,
                    mut strategy, _exec_venue) -> BacktestResult {
        strategy.on_init(&mut ctx);
        for bar in bars {
            for tick in generate_ticks_from_bar(bar, &tick_config) {
                strategy.on_tick(&mut tick_ctx, SubscriptionId(sub_idx));
                // apply TradeAction::{Open, Close, Modify} …
                // check_sl_tp_trigger → close positions on SL/TP …
            }
            equity_curve.push(EquityPoint { ts: now, equity });
        }
        strategy.on_deinit(&mut ctx);
        BacktestResult { config, equity_curve, trades, stats, order_events }
    }
}

16 · Outbound adapter

The same strategy contract, driven by real time instead of a replay: a tokio task that waits on price events and a stop signal.

async fn start_session(&self, config, strategy, exec_venue) -> Result<LiveSessionHandle, Error> {
    let (stop_tx, stop_rx) = oneshot::channel::<()>();
    tokio::spawn(async move {
        run_live_session(config, strategy, exec_venue, bar_source, tick_source, stop_rx).await
    });
    Ok(LiveSessionHandle::new(session_id, stop_tx))
}

Ids & stateAtomicU64 counters for OrderId/PositionId; positions in a RwLock<PaperBrokerState>
Where a real broker would goa new crate implementing the same ExecutionVenue trait — swap one line in the composition root, nothing inner changes
AgnostixCrate: crates/adapters/outbound_paper_broker/ (lib.rs, 310 lines). Handles all three ExecutionCommand variants and answers with an ExecutionReport of domain Order/Execution/Position values.

18 · Outbound adapter

DuckDB repositories — implement the repository ports

One concrete type per port, all in the adapters_outbound_duckdb crate, all built on a shared DuckDbPool.

PortDuckDB implementation

BacktestTradeRepositoryDuckDbBacktestTradeRepository (state DB)

19 · Strategy wiring

StrategyRegistry & the shipped strategies

Who actually implements Strategy? Two strategies today, registered by name in a registry that implements StrategyRegistryPort.

  • StrategyRegistry (crates/sdk/strategy_api/src/lib.rs) — a name → factory map; create(name, params) returns Option<Box<dyn Strategy>>.
  • PriceMomentum (crates/app/src/strategies.rs) — demo: once per H1 bar, buy if the last closed H1 close beat the one before, sell if it fell.
  • SMACross (same file) — the running example: fast SMA 13 vs slow SMA 21 on a configurable timeframe; buy on upward cross at ctx.ask() with SL/TP in pips, sell on downward cross at ctx.bid(). Params (lot_size, fast_period, ma_timeframe, …) parsed from StrategyParams with safe defaults.
// crates/app/src/strategies.rs — verbatim

AgnostixStrategies see only the SDK surface (strategy_api::* re-exports the port vocabulary: Ctx, H1, price_close, SubscriptionId…). They cannot reach a database, the engine, or the broker — the deepest proof that the port boundary works.
Show me SMACross's signal
fn on_tick(&mut self, ctx: &mut Ctx<'_>, sub: SubscriptionId) {
    if !ctx.is_bar_open(tf) { return; }
    let fast_1 = ctx.SMA(tf, self.cfg.fast_period, price_close, 1);
    let slow_1 = ctx.SMA(tf, self.cfg.slow_period, price_close, 1);
    // … fast_2/slow_2 for the previous bar …
    if fast_2 <= slow_2 && fast_1 > slow_1 {
        ctx.buy(sub, units, sl, tp);        // entry at ctx.ask()
    } else if fast_2 >= slow_2 && fast_1 < slow_1 {
        ctx.sell(sub, units, sl, tp);       // entry at ctx.bid()
    }
}

22 · Full picture

The whole picture

Nothing on the diagram is new — you watched every ring appear. Now derive the rule instead of memorizing it.

domain  ←  usecases  ←  ports  ←  adapters  ←  app (container.rs)

crates/domain          knows: nothing outside itself (+ time crate)
crates/usecases        knows: domain + ports
crates/ports           knows: domain            (traits owned by the inside)
crates/adapters/*      know:  ports + domain + their tech (DuckDB, Axum, tokio)
crates/app             knows: everyone          (names concrete types, once)

Now derive the dependency rule

Every arrow of knowledge points inward. The engine knows the Strategy trait, never SMACross. The use case knows TradingEnginePort, never BacktestEngine. The strategy knows Ctx, never DuckDB. Replace any outer box and no inner box recompiles.

Where does "connect a real broker" go?
A new crate implementing ExecutionVenue. Change one line in container.rs (PaperBroker::default() → your broker). The live engine, use cases and strategies are untouched.
Where does "a new strategy" go?
A type implementing Strategy plus one reg.register("name", factory) line in crates/app/src/strategies.rs. It is instantly available to both backtest and live trading.
Where does "trade on real market data feeds" go?
Implement LiveBarSource / LiveTickSource and pass them as LiveTradingDeps to build_container_with_live. The engine loop already consumes both.
Where does "slippage simulation" go?
Inside BacktestEngine / tick_simulation.rs — it is a detail of how fills are simulated, invisible to the ports. If it needs configuration, extend TickSimulationConfig in the domain.
Where does "backtest progress % and pause" go?
The Job context: backtest_jobs_uc.rs, backtest_worker.rs, BacktestJob*Repository. It wraps this context's engine (run_backtest_with_progress_counter) without changing it.

23 · Runtime

Follow one backtest through the architecture

Our running example: POST /api/v1/backtests/sync with "SMACross", EURUSD, Jan 2024, $10,000. Click a step or use the buttons — the diagram lights up the path.

  1. Client → HTTP adapterThe frontend posts JSON to /api/v1/backtests/sync. The Axum handler parses dates, forces M1 subscriptions, defaults missing fields.
  2. Handler → RunBacktestPort → RunBacktestThe handler holds Arc<dyn RunBacktestPort> and calls execute(dto::Input). The use case behind it wakes up.
  3. Use case → StrategyRegistryPortstrategy_registry.create("SMACross", &params) → Box<dyn Strategy>. Unknown name would stop here with Error::NotFound.
  4. Use case → BarRepository (DuckDB)fetch_range(EURUSD, M1, Jan 2024) plus M5…D1 series for multi-timeframe access → SubscriptionState with bars and tf_bars.
  5. Use case → TradingEnginePortengine.run_backtest(config, subscription_states, IndicatorDataBundle::new(), params, strategy, exec_venue) — a plain synchronous call.
  6. Engine: bars → ticks → strategyEach M1 bar becomes ~60 simulated Ticks (TickSimulationConfig::forex()). Every tick: strategy.on_tick(ctx, sub). SMACross acts only when ctx.is_bar_open(H1).
  7. Engine applies TradeActions + SL/TPA crossover pushes TradeAction::Open; the engine fills it at ask, opens a Position, records an OrderLifecycleEvent. Every later tick runs check_sl_tp_trigger; a hit closes the position and books realized_pnl.
  8. Engine → BacktestResultAfter the last bar: on_deinit, force-close leftovers, compute BacktestStats (net profit, max drawdown, win rate) → BacktestResult returns to the use case.
  9. Result → JSON → clientThe handler maps equity curve, trades and stats to response structs. The three Backtest*Repository ports were not touched — persistence is the Job context's flow.

24 · Runtime

Follow one live session: start, trade, stop

Same strategy, live prices. Reminder: no HTTP route exists yet — the caller invokes StartLiveTradingPort directly (e.g. from wiring or tests).

  1. Caller → StartLiveTradingPortexecute(Input { strategy_name: "SMACross", subscriptions: [EURUSD@M1], initial_balance: None → 10,000 }).
  2. Use case → StrategyRegistryPortSame registry, same SMACross code as the backtest — that is the payoff of the shared Strategy trait.
  3. Use case → LiveTradingEnginePortlive_engine.start_session(LiveTradingConfig { session_id: uuid, … }, strategy, exec_venue).
  4. Engine spawns the session tasktokio::spawn(run_live_session(…)); the loop calls strategy.on_init, then bar_source.subscribe(subs) and optionally tick_source.subscribe(subs). A LiveSessionHandle (id + oneshot sender) returns immediately.
  5. Session recorded, id returnedLiveSessionManager.add_session(LiveSession { id, strategy_id, subscriptions, started_at, handle }) → Output { session_id: "3f2a…" }.
  6. A tick arrives → a trade executestokio::select! yields a tick → process_tick → strategy.on_tick pushes TradeAction::Open → the engine builds ExecutionCommand::OpenMarket → exec_venue.execute(cmd).await → the PaperBroker fills it and returns an ExecutionReport.
  7. Caller → StopLiveTradingPortexecute(Input { session_id: "3f2a…" }) → session_manager.stop_session removes the record and calls handle.stop() — the oneshot fires.
  8. The loop shuts down cleanlyThe stop_rx arm of tokio::select! wins, the loop breaks ("Live session {} stopping"), strategy.on_deinit runs, the task ends. Output: { session_id, stopped: true }.
