00 · Before architecture

Why does this exist?

Agnostix stores decades of one-minute price history and answers questions about it: draw a chart, zoom out to hourly candles, overlay a moving average.

The Market Data context has exactly three jobs:

  1. Get price history in. A text file with millions of lines like EURUSD,20240102,090000,1.0946,… becomes rows in a database.
  2. Serve it back at any zoom level. The raw data is 1-minute candles; a chart may want 5-minute, hourly, or daily candles — either precomputed or computed on the fly.
  3. Compute indicators on top of it. A 20-period SMA, an RSI, a MACD — derived numbers a chart overlays on the candles.
The problem with the naive version. Put the SQL, the file parsing, and the HTTP handlers in one module and every one of these decisions gets welded to DuckDB and Axum: you cannot test the resampling rules without a database file, you cannot swap the storage engine, and every new indicator touches the web layer.
How do we arrange this so that the database (DuckDB) and the delivery mechanism (HTTP) are replaceable — without their details leaking into the parts that decide what a bar, a timeframe, or an indicator means?

The one running example

One request, reused in every chapter: a chart asks for hourly EURUSD candles for January 2nd, 2024.

GET /api/v1/bars?symbol=EURUSD&tf=H1
     &from=2024-01-02T00:00:00Z&to=2024-01-03T00:00:00Z&limit=500

→ one of the bars that comes back:
  EURUSD · H1 · 2024-01-02 09:00 UTC
  open 1.0946 · high 1.0953 · low 1.0940 · close 1.0951 · volume 18240

01 · The core

Start with the domain core

What does this system fundamentally talk about? Bars, timeframes, symbols, time ranges, and indicator definitions. Nothing else exists yet — no database, no HTTP, no async.

ConceptThe innermost ring of a hexagonal architecture holds the vocabulary of the business: the types every other layer speaks in. It depends on nothing further out — the arrows all point inward.
AgnostixLives in crates/domain. Its Cargo.toml lists exactly one dependency: the time crate (for UTC timestamps). No DuckDB, no Axum, no tokio.

Classify it — these are not eight entity classes

The Market Data core sorts into three kinds:

KindMembersIn Rust this becomes
Records — typed factsBar, IndicatorPointplain struct with public fields
Values / vocabularySymbol, Timeframe, RangeUtc, IndicatorKindnewtype / enum, Eq + Hash, immutable
Specs — "what to compute"IndicatorDef, MacdParamsplain struct, consumed by adapters

The only pure rules (deterministic functions) in this context are Timeframe::minutes() and Timeframe::floor(). Everything else in the core is data, not behaviour — a deliberate choice: the heavy computation (SQL aggregation, indicator math) lives in adapters.

What it knows
What a candlestick is, which timeframes exist, that a range is half-open [start, end), what parameters an SMA/EMA/RSI/MACD takes.
What it must NOT know
Where bars are stored, what SQL looks like, what an HTTP query string is, that DuckDB or Axum exist.
Who calls it
Every outer ring — use cases, ports, adapters all speak these types.
What it calls
Only std and the time crate.

02 · Core · Bar

Bar — one candlestick, five numbers

A bar summarises price action over one period: the first price (open), the extremes (high, low), the last price (close), and how much traded (volume).

EURUSD · H1 · 2024-01-02 09:00 UTC open 1.0946 ✓ first trade of the hour high 1.0953 ✓ highest price seen low 1.0940 ✓ lowest price seen close 1.0951 ✓ last trade of the hour volume 18240 ✓ total quantity traded

Why a struct and not a class with methods?

A bar is a fact — it happened, it never changes. The code models it as a plain record: eight public fields, Clone, no constructor logic.

AgnostixHonest note. The doc comment in ohlcv.rs states the invariants (high >= max(open, close), low <= min(open, close), volume >= 0) but says they are not enforced at compile time — any code can construct a Bar with nonsense values. The database and ingestion format are trusted to deliver consistent rows.
Show me the code
// crates/domain/src/ohlcv.rs
#[derive(Debug, Clone)]
pub struct Bar {
    pub symbol: Symbol,      // what is traded
    pub tf: Timeframe,       // period of this bar
    pub ts: OffsetDateTime,  // UTC start of the period
    pub open: f64,
    pub high: f64,
    pub low: f64,
    pub close: f64,
    pub volume: u64,
}

03 · Core · Timeframe

Timeframe — how much time one candle covers

Seven fixed zoom levels. That's the whole vocabulary: there is no "custom timeframe" in this system.

M1 1 minute ✓ canonical — this is what gets ingested M5 5 minutes ✓ derived M15 15 minutes ✓ derived M30 30 minutes ✓ derived H1 1 hour ✓ derived — our running example H4 4 hours ✓ derived D1 1 day ✓ derived

The two pure rules of the context

  1. minutes() — converts a timeframe to its length: M1→1, H1→60, D1→1440. Resampling math is built on this.
  2. floor(ts) — snaps a timestamp to the start of its bar: 09:37:12 floored to H1 is 09:00:00. Deterministic, UTC, no I/O.
AgnostixAn enum with Copy + Ord + Hash in crates/domain/src/timeframe.rs. Because it's an enum, an invalid timeframe cannot exist past the parsing edge — the HTTP adapter turns the string "H1" into Timeframe::H1 once, and the rest of the system never re-validates.
Show me the code
// crates/domain/src/timeframe.rs
pub enum Timeframe { M1, M5, M15, M30, H1, H4, D1 }

impl Timeframe {
    pub fn minutes(self) -> i64 {
        match self { M1 => 1, M5 => 5, M15 => 15, M30 => 30,
                     H1 => 60, H4 => 240, D1 => 1440 }
    }
    /// Floors a timestamp to the start of the bar for this timeframe (UTC).
    pub fn floor(self, ts: time::OffsetDateTime) -> time::OffsetDateTime { /* … */ }
}

04 · Core · Symbol & RangeUtc

Symbol & RangeUtc — "what" and "when"

Every question this context answers has the shape: which instrument, which timeframe, which time window? Two small value objects pin down the first and last part.

Symbol("EURUSD") ✓ which instrument RangeUtc { start: 2024-01-02T00:00Z, ✓ inclusive end: 2024-01-03T00:00Z } end is EXCLUSIVE — the midnight bar of Jan 3 is NOT included

Why bother wrapping a String?

Symbol is a newtype around String: immutable, hashable, equal by value. It exists so function signatures say what they take — fetch_range(symbol, tf, range) reads like the question it answers, and you cannot accidentally pass a file path where a symbol goes.

RangeUtc encodes one convention once — half-open [start, end) — so every repository, SQL query, and use case agrees on which boundary bar belongs to which page of results.

Show me the code
// crates/domain/src/symbol.rs
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub struct Symbol(String);
impl Symbol {
    pub fn new<S: Into<String>>(s: S) -> Self { Self(s.into()) }
    pub fn as_str(&self) -> &str { &self.0 }
}

// crates/domain/src/slice.rs
#[derive(Debug, Clone)]
pub struct RangeUtc {
    pub start: OffsetDateTime, // inclusive
    pub end: OffsetDateTime,   // exclusive
}

Files: crates/domain/src/symbol.rs, crates/domain/src/slice.rs. Note: Symbol enforces no format — any string is accepted.

05 · Core · Indicator definitions

IndicatorDef — a recipe, not a calculator

An indicator is a derived line drawn over the candles — a 20-period average, a momentum score. The core defines how to describe one; it deliberately does not compute it.

IndicatorDef { "compute a 20-period SMA on H1 bars" kind: IndicatorKind::SMA, ✓ SMA | EMA | RSI | MACD period: 20, source_tf: Timeframe::H1, macd: None, Some(MacdParams{fast,slow,signal}) for MACD } → output: Vec<IndicatorPoint { ts, value }> one number per bar

The lifecycle in one line

describe (core: IndicatorDef) → request (use case) → compute (adapter: an indicator engine) → points (core: IndicatorPoint). The core owns both ends; the middle is replaceable.

AgnostixThe module doc in indicator.rs says it outright: "This module defines what indicators are… The actual computation happens in adapters… to keep the domain pure."
Also in this file: the indicator SDK traits

indicator.rs additionally defines an MT4-style authoring API for custom indicators: traits Series (bars-ago indexing: 0 = current), Buffer, Indicator, and the newer IndicatorV2 with SeriesData/Buffers/Params. These are consumed by the custom indicator engine adapter (chapter 18) and re-exported through crates/sdk/indicator_api. They are contracts, not computations — still zero I/O.

pub trait IndicatorV2: Default + 'static {
    const NAME: &'static str;
    const OUTPUTS: &'static [&'static str];   // e.g. ["main","signal"]
    fn on_bar(&mut self, series: &SeriesData<'_>, out: &mut Buffers<'_>);
}

06 · The next layer

Use cases — what can the system do?

Nouns were the core. These are the verbs. Look at the diagram: a new box has appeared around the old one — the core did not move.

Six use cases, and they follow one pattern:

  1. query_bars — fetch stored candles for a symbol / timeframe / range.
  2. resample_bars — aggregate M1 candles into a bigger timeframe, on the fly.
  3. materialize_timeframes — do that resampling once and store the result (all six derived timeframes by default).
  4. compute_indicator — single-line indicators (SMA/EMA/RSI) as one series of points.
  5. compute_indicator_buffers — multi-line indicators (MACD = main + signal + hist) as named series.
  6. ingest_bars — load a bar text file into storage.
ConceptA use case is one operation the application offers, written against interfaces for everything it needs. It orchestrates; it does not know SQL or HTTP.
AgnostixOne file per use case in crates/usecases/src/*_uc.rs. Each is a small struct holding an Arc to the repository trait it needs, implementing its inbound port's single method: async fn execute(input) -> Result<Output, Error>.
The shared shape, verbatim
// crates/usecases/src/query_bars_uc.rs — the whole file, minus imports
pub struct QueryBars<R: ?Sized> { repo: Arc<R> }
impl<R: ?Sized> QueryBars<R> {
    pub fn new(repo: Arc<R>) -> Self { Self { repo } }
}

#[async_trait]
impl<R> QueryBarsPort for QueryBars<R>
where R: BarRepository + 'static + ?Sized {
    async fn execute(&self, input: dto::Input) -> Result<dto::Output, Error> {
        let bars = self.repo
            .fetch_range(&input.symbol, input.tf, &input.range, input.limit)
            .await?;
        Ok(dto::Output { bars })
    }
}

Generic over R: BarRepository + ?Sized — the use case compiles against the trait, never a concrete database type.

The workhorse behind every chart render.

08 · Use case · resample_bars & materialize_timeframes

Resample & Materialize — two halves of one lifecycle

Only M1 bars are ingested. Every other timeframe is derived — either computed when asked (resample) or computed once and stored (materialize).

60 × M1 bars (09:00 … 09:59) ──aggregate──▶ 1 × H1 bar (09:00) open = first open high = max(high) close = last close low = min(low) volume = sum
  1. ResampleBars — "show me H1 candles now": calls ResampleRepository::resample_range(symbol, src_tf, dst_tf, range, limit), returns bars, stores nothing.
  2. MaterializeTimeframes — "precompute my zoom levels": for each target timeframe calls ResampleRepository::materialize_range(symbol, tf, range), which writes into the bars_m5 … bars_d1 tables. Returns { rows_written, targets }.
AgnostixMaterializeTimeframes contains the one piece of real decision logic in this layer: if the caller passes an empty target list, it defaults to all six derived timeframes — vec![M5, M15, M30, H1, H4, D1] — and loops materialize_range over them, summing rows written.
Show me the code
// crates/usecases/src/materialize_timeframes_uc.rs
let targets = if input.targets.is_empty() {
    vec![Timeframe::M5, Timeframe::M15, Timeframe::M30,
         Timeframe::H1, Timeframe::H4, Timeframe::D1]
} else { input.targets.clone() };

let mut total = 0u64;
for tf in &targets {
    total += self.repo.materialize_range(&input.symbol, *tf, &input.range).await?;
}
Ok(dto::Output { rows_written: total, targets })

Files: crates/usecases/src/{resample_bars,materialize_timeframes}_uc.rs, port DTOs in crates/ports/src/inbound/{resample_bars,materialize_timeframes}.rs

09 · Use case · compute_indicator & compute_indicator_buffers

ComputeIndicator — one line or many

Two use cases, same inputs, different output shapes — because indicators come in two shapes.

  1. ComputeIndicator → Output { points: Vec<IndicatorPoint> }. For single-line indicators: SMA, EMA, RSI.
  2. ComputeIndicatorBuffers → Output { buffers: BTreeMap<String, Vec<IndicatorPoint>> }. For multi-line indicators: MACD returns "main", "signal", "hist".
Input { def: IndicatorDef{SMA, period:20, source_tf:H1}, symbol: EURUSD, tf: H1, range: […), warmup: Some(20), limit: None } ▲ warmup: fetch 20 extra bars BEFORE the range so the first SMA value is real

Warmup, plainly: a 20-period average at 00:00 needs the 20 bars before 00:00. The warmup field says how many extra earlier bars the engine may pull; results are trimmed back to the requested range before returning.

Required dependencies — via ports
IndicatorRepository (outbound) — both use cases share it: compute_points for one, compute_buffers for the other.
Who calls them
GET /api/v1/indicators/points and GET /api/v1/indicators/buffers.
Architecture detail

Both use cases are pure pass-throughs to IndicatorRepository. The interesting part is who implements that port: not the database, but an in-memory engine adapter that itself calls back into BarRepository — an adapter standing on other ports. See chapter 18.

Files: crates/usecases/src/{compute_indicator,compute_indicator_buffers}_uc.rs, crates/ports/src/inbound/{compute_indicator,compute_indicator_buffers}.rs

11 · Why ports exist

The application needs help

The use cases promise a lot they cannot do alone. Look at the diagram: unnamed sockets have appeared on the bottom edge of the application.

QueryBars needs stored candles back fast. Should it know how DuckDB pages a 25-year minute-bar table? No.
ResampleBars needs 60 bars collapsed into 1. Should it know SQL window functions? No.
ComputeIndicator needs an SMA over thousands of closes. Should it care whether that runs in SQL or in a Rust loop? No.
ConceptA port is a contract owned by the inner layer, written in the inner layer's vocabulary (Symbol, Timeframe, RangeUtc — never "table" or "connection"). Whoever fulfils it lives outside and depends inward. This is dependency inversion: the application names its needs; technology applies for the job.

This context declares two kinds:

  1. Inbound ports — what the world may ask of us: QueryBarsPort, ResampleBarsPort, MaterializeTimeframesPort, ComputeIndicatorPort, ComputeIndicatorBuffersPort, IngestBarsPort. Each is one execute(dto::Input) → dto::Output, implemented by the use case of the same name.
  2. Outbound ports — what we ask of the world: BarRepository, ResampleRepository, IndicatorRepository, MetadataRepository, LiveBarSource, LiveTickSource. The next five chapters name them.
The shared error contract

Every port returns Result<_, ports::Error> with four variants — the whole failure vocabulary of the context:

// crates/ports/src/error.rs
pub enum Error {
    Validation(String),          // bad input → HTTP 400
    NotFound(String),            // no such data → HTTP 404
    Repository(anyhow::Error),   // storage/compute blew up → HTTP 500
    Internal(String),            // lock poisoning etc. → HTTP 500
}

The HTTP status mapping happens in the inbound adapter's map_err (chapter 19) — the port layer itself knows nothing about HTTP codes.

12 · Outbound port

BarRepository — store and fetch candles

The primary storage contract: three promises about bars.

// crates/ports/src/outbound/bar_repository.rs
#[async_trait]
pub trait BarRepository: Send + Sync {
    /// Loads bars from a text file into the database.
    async fn ingest_txt(&self, txt_path: PathBuf, assume_utc: bool)
        -> Result<IngestReport, Error>;

    /// Bars for symbol+timeframe in [start, end), oldest first.
    async fn fetch_range(&self, symbol: &Symbol, tf: Timeframe,
        range: &RangeUtc, limit: Option<usize>) -> Result<Vec<Bar>, Error>;

    /// The most recent N bars, returned oldest first.
    async fn fetch_latest(&self, symbol: &Symbol, tf: Timeframe, n: usize)
        -> Result<Vec<Bar>, Error>;
}

The doc-comments carry real contract weight: bars come back in chronological order, oldest first — even fetch_latest, which reads newest-first internally and must reverse. IngestReport is { symbol, rows_loaded }.

AgnostixUsed by three parties: QueryBars and IngestBars (use cases), and — perhaps surprisingly — the indicator engines, which fetch their input bars through this same port (chapter 18). One contract, many leases.

13 · Outbound port

ResampleRepository — collapse timeframes

Two promises: aggregate and return, or aggregate and store.

// crates/ports/src/outbound/resample_repository.rs
#[async_trait]
pub trait ResampleRepository: Send + Sync {
    /// Resample src_tf → dst_tf on the fly; stores nothing.
    async fn resample_range(&self, symbol: &Symbol,
        src_tf: Timeframe, dst_tf: Timeframe,
        range: &RangeUtc, limit: Option<usize>) -> Result<Vec<Bar>, Error>;

    /// Resample from M1 and persist into the dst_tf table.
    /// Returns the number of bars written.
    async fn materialize_range(&self, symbol: &Symbol,
        dst_tf: Timeframe, range: &RangeUtc) -> Result<u64, Error>;
}

The OHLCV aggregation rules are spelled out in the trait docs — first open, max high, min low, last close, summed volume — so any implementation is held to the same math. Note the asymmetry: resample_range takes a source timeframe, materialize_range is documented to assume the source is M1.

AgnostixUsed by ResampleBars and MaterializeTimeframes, and by the default indicator engine when its warmup fetch needs derived timeframes.

14 · Outbound port

IndicatorRepository — do the math somewhere else

The application hands over a recipe (IndicatorDef) and coordinates; the implementor computes.

// crates/ports/src/outbound/indicator_repository.rs
#[async_trait]
pub trait IndicatorRepository: Send + Sync {
    async fn compute_points(&self, def: &IndicatorDef, symbol: &Symbol,
        tf: Timeframe, range: &RangeUtc, warmup: Option<u32>,
        limit: Option<usize>) -> Result<Vec<IndicatorPoint>, Error>;

    /// Named buffers like {"main": […], "signal": […]}.
    async fn compute_buffers(&self, def: &IndicatorDef, symbol: &Symbol,
        tf: Timeframe, range: &RangeUtc, warmup: Option<u32>,
        limit: Option<usize>)
        -> Result<BTreeMap<String, Vec<IndicatorPoint>>, Error>;
}

The warmup contract lives in the docs: if warmup is None, the implementation should choose a sensible default (e.g. the indicator period); either way the caller receives points only inside the requested range.

AgnostixThe name says "Repository" but nothing here is stored — both implementations compute in memory per request. The port abstracts computation, which is exactly the point: SQL, Rust loop, or GPU, the use case cannot tell.

17 · Outbound adapter

outbound_duckdb — implements BarRepository, ResampleRepository, MetadataRepository

The first concrete technology enters the picture — three structs, one per port, all sharing a single serialized DuckDB connection.

Tech detailHow the adapter handles it
DuckDB dislikes concurrent access in single-file modeDuckDbPool: one shared connection behind a Mutex; every operation goes through with_conn
DuckDB calls are blocking; the app is asynctokio::task::spawn_blocking inside with_conn — the async runtime never stalls on SQL
Seven timeframes, seven tablesutil::table_for(tf) maps Timeframe::H1 → "bars_h1" etc. (schema in migrations/0001_bars.sql)
Bulk file ingestioningest_txt is one SQL statement: INSERT INTO bars_m1 SELECT … FROM read_csv('file') — the file never passes through Rust row by row
Resampling mathSQL window functions: first_value(open), last_value(close), max(high), min(low), sum(volume), grouped by util::bucket_expr_minutes (epoch-math time bucketing)
Idempotent materializationmaterialize_range = DELETE the window from the target table, then INSERT the fresh aggregation — re-running never duplicates
Timestamp fidelityreads via epoch_ms(ts), reconstructs OffsetDateTime from epoch nanos
AgnostixWhere would a PostgreSQL implementation go? A sibling crate adapters/outbound_postgres implementing the same three traits — and nothing inward of the ports would change. The composition root would swap one constructor.
Show me fetch_range
// crates/adapters/outbound_duckdb/src/bar_repository.rs (trimmed)
async fn fetch_range(&self, symbol: &Symbol, tf: Timeframe,
                     range: &RangeUtc, limit: Option<usize>) -> Result<Vec<Bar>, Error> {
    let tname = table_for(tf).to_string();          // "bars_h1"
    self.pool.with_read_conn(move |conn| {
        let sql = format!(
            "SELECT symbol, epoch_ms(ts) as ts_ms, open, high, low, close, volume
             FROM {} WHERE symbol = ?1 AND ts >= ?2 AND ts < ?3
             ORDER BY ts ASC LIMIT ?4", tname);
        // … map rows → Vec<Bar> …
    }).await.map_err(Error::Repository)
}

18 · Outbound adapter

Indicator engines — adapters that stand on ports

IndicatorRepository has two in-tree implementations, both pure Rust, both selectable at boot. Neither talks to DuckDB directly — they fetch bars through the same ports the use cases use.

  1. Default engine — adapters_outbound_indicator_engine::IndicatorEngine. Hard-coded SMA/EMA/RSI/MACD algorithms over Vec<Bar>. Depends on BarRepository + ResampleRepository to get its input bars (with warmup padding), trims results back to the requested range.
  2. Custom engine — adapters_outbound_custom_indicator_engine::IndicatorEngine. Runs indicators written against the MT4-style SDK traits from domain::indicator (bars-ago Series, named output Buffers). Depends on BarRepository only. Selected by env var INDICATOR_ENGINE=custom.
MACD via compute_points? the default engine answers honestly: compute_points(MACD) → delegates to compute_buffers, returns buffers["main"] compute_buffers(MACD) → { "main": […], "signal": […], "hist": […] }
AgnostixThis is the pattern worth remembering: an adapter may depend on ports. The engine implements IndicatorRepository (its outward face) while consuming BarRepository (its inward needs) — composition stays legal because both arrows still point at contracts, never at concrete types.

19 · Inbound adapter

inbound_http — drives the application

An Axum router that translates the web's vocabulary (query strings, JSON, status codes) into the application's vocabulary (DTOs, domain types, ports::Error) — and back.

RouteCalls
GET /api/v1/barsQueryBarsPort (falls back to ResampleBarsPort)
GET /api/v1/resampleResampleBarsPort (always src_tf = M1)
GET /api/v1/indicators/pointsComputeIndicatorPort
GET /api/v1/indicators/buffersComputeIndicatorBuffersPort
GET /api/v1/symbolsMetadataRepository::list_symbols — outbound port, directly
GET /api/v1/series/metaMetadataRepository::series_meta — outbound port, directly

Translation at the edge, in both directions:

  1. In: parse_tf("H1") → Timeframe::H1, parse_instant accepts RFC3339 or epoch seconds, parse_indicator_kind("sma") → IndicatorKind::SMA.
  2. Out: Bar → Candle { time: epoch seconds, o,h,l,c,v } — shaped for the lightweight-charts frontend; map_err turns Validation→400, NotFound→404, Repository/Internal→500.
AgnostixHonest notes — three real asymmetries.
1. Policy in the adapter: the "materialized table empty → resample M1 on the fly" fallback lives in the get_bars handler, not in a use case. A second inbound adapter (CLI, gRPC) would have to duplicate it.
2. Outbound port called from inbound adapter: the metadata endpoints skip the application layer entirely (chapter 15).
3. Not everything is exposed: IngestBarsPort and MaterializeTimeframesPort have no routes — operationally those run via scripts/duckdb_ingest.sh.

20 · Assembly

Composition root — who names the concrete types?

Exactly one place in the whole system spells out "BarRepository means DuckDbBarRepository": build_container in crates/app/src/container.rs. Read it downward — adapters first, then use cases plugged onto them.

21 · Full picture

The whole picture

Nothing on the diagram is new — you watched every ring appear. Now derive the rule instead of memorising it.

browser ──▶ inbound_http ──▶ inbound ports ──▶ usecases ──▶ outbound ports ──▶ outbound_duckdb / engines
                                                   │                                    │
                                                   ▼                                    ▼
                                               domain  ◀────────── everyone speaks domain types

source-code dependencies: domain ← ports ← usecases ← adapters ← app (composition root)

Check it against the crate manifests: domain depends on nothing (but time); ports depends on domain; usecases depends on ports + domain; every adapter depends on ports + domain; only app depends on everything. Runtime calls flow outside-in and back; compile-time dependencies all point inward. That inversion — the port traits sitting between usecases and adapters — is the whole trick.

Where does "support a 2-hour timeframe" go?
Four touches, inside-out: Timeframe::H2 variant + minutes()/floor() arms (domain), table_for + a migration for bars_h2 (DuckDB adapter), parse_tf (HTTP adapter), default target list in MaterializeTimeframes if it should precompute. No port signatures change.
Where does "add a Bollinger Bands indicator" go?
A new IndicatorKind variant (domain) and a computation arm in the engine(s) (adapter) — or, with the custom engine, just a new IndicatorV2 impl registered against the SDK. Use cases and ports are untouched: they already move IndicatorDef and buffers generically.
Where does "store bars in PostgreSQL" go?
A new crate adapters/outbound_postgres implementing BarRepository, ResampleRepository, MetadataRepository, plus a constructor swap in container.rs. Domain, ports, use cases, HTTP: zero diffs.
Where does "connect a real-time price feed" go?
A crate implementing LiveBarSource (and optionally LiveTickSource), passed into build_container_with_live as LiveTradingDeps. The ports and the consuming engine already exist (chapter 16) — this is the one ring with an empty socket today.
Where does the get_bars fallback policy *belong*?
Today: in the HTTP handler (chapter 19, honest note). By the dependency rule it belongs in QueryBars (or a dedicated use case) so every future inbound adapter inherits it. Moving it is a pure inward refactor: give QueryBars a second port (ResampleRepository) and delete the handler branch.

22 · Runtime · happy path

Follow one chart request through the rings

The running example, end to end: hourly EURUSD candles for Jan 2, 2024. Click a step or use the buttons — the diagram lights up the path.

  1. Browser → inbound adapterGET /api/v1/bars?symbol=EURUSD&tf=H1&from=…&to=…&limit=500 hits the Axum route registered in router().
  2. Edge translation, inwardget_bars parses strings into domain types: parse_tf("H1") → Timeframe::H1, parse_instant → OffsetDateTime, then builds query_dto::Input { symbol, tf, range, limit }. Bad input stops here as Validation → 400.
  3. Inbound port → use casest.query_bars.execute(input) — the handler holds Arc<dyn QueryBarsPort>; behind it is the QueryBars use case the container built.
  4. Use case → outbound portQueryBars calls self.repo.fetch_range(&symbol, tf, &range, limit) — speaking only BarRepository, unaware of DuckDB.
  5. Port → DuckDB adapterDuckDbBarRepository::fetch_range: table_for(H1) → "bars_h1", then SELECT … WHERE symbol = ?1 AND ts >= ?2 AND ts < ?3 ORDER BY ts ASC LIMIT ?4.
  6. Inside the adapterDuckDbPool.with_read_conn → spawn_blocking + mutex → rows stream back and are rebuilt into Vec<Bar> via epoch_ms timestamps.
  7. Back up the stackThe Vec<Bar> travels adapter → port → use case (dto::Output { bars }) → handler, as domain types the whole way.
  8. Edge translation, outwardHandler maps each Bar → Candle { time: epoch secs, open, high, low, close, volume } and replies with BarsResponse JSON. The browser draws 24 hourly candles.

23 · Runtime · repair path

When the shelf is empty — fallback and errors

Same request, but nobody has materialized H4 bars yet. The system answers anyway.

  1. First attempt: query the materialized tableGET /api/v1/bars?…&tf=H4 → QueryBarsPort → fetch_range on bars_h4 → returns 0 bars. Not an error — an empty Vec.
  2. The handler decidesget_bars checks: out.bars.is_empty() && tf != Timeframe::M1 — true. (This policy lives in the adapter; see chapter 19's honest note.)
  3. Second attempt: resample on the flyHandler calls ResampleBarsPort::execute with src_tf: M1, dst_tf: H4 over the same range.
  4. Use case → ResampleRepositoryResampleBars forwards to resample_range(symbol, M1, H4, range, limit).
  5. DuckDB aggregates 240 minutes into 1 barbucket_expr_minutes(240, "ts") bins timestamps; window functions take first open / last close, max(high), min(low), sum(volume) per bucket.
  6. Fresh H4 candles flow backSame JSON shape as the happy path — the browser cannot tell the bars were computed seconds ago. (Running MaterializeTimeframes later makes the first attempt succeed.)
  7. And when things actually failmap_err translates the port error, not the technology: Validation → 400 ("invalid timeframe"), NotFound → 404, Repository/Internal → 500. DuckDB's own error text surfaces only inside the 500 body, wrapped as Error::Repository(anyhow).

24 · Confidence

How the architecture makes testing easier

AgnostixHonest note first. As of commit 4d46b79, the Market Data context has no automated tests. Grepping #[cfg(test)] finds tests only in the Trading/Job contexts (backtest_job_state.rs, backtest_worker.rs, the trading engine). What the domain does have is runnable doctests — the ```rust examples in ohlcv.rs, symbol.rs, slice.rs, timeframe.rs compile and assert under cargo test --doc.

The seams are already in place, so here is what each layer's test would look like — this table is a map of the architecture's testing affordances, not of an existing suite:

LayerHow it is testedReal / fake
Domain (Timeframe::floor, minutes)plain unit tests + existing doctests; pure functions, no setupeverything real
Use cases (QueryBars, …)implement BarRepository/ResampleRepository/IndicatorRepository with an in-memory fake; assert pass-through, default-targets logic, error propagationfake repositories — the generics (QueryBars<R: BarRepository>) accept them today
Indicator enginesfeed a fixed Vec<Bar> through a fake BarRepository; assert SMA/EMA/RSI/MACD values and warmup trimmingfake bar source, real math
DuckDB adapterintegration test against a temp .duckdb file: ingest a small fixture, fetch_range, resample_range, materialize_range round-tripsreal DuckDB, real SQL
HTTP adapterrouter(HttpState{…fakes…}) + tower::ServiceExt::oneshot: assert parsing, the empty→resample fallback, and map_err status codesfake ports behind Arc<dyn …Port>
Composition rootbuild_container against temp DB paths; assert it wires without panickingreal everything, tiny data

Notice what makes each row cheap: every dependency crosses a trait object or a generic bound, so substituting a fake is a constructor argument, not a mocking framework.
