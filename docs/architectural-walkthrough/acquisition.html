00 · Before architecture

Why does this architecture exist?

Forget hexagons for a moment. Here is what the program has to do.

AgnoForge's market-acquisition service has four jobs:

  1. Ask a market-data provider (today: Binance) for Bars — OHLCV candles.
  2. Store those Bars, exactly as the provider reported them.
  3. Notice when Bars that should exist are missing.
  4. Answer one question for everyone else: can this date range be trusted?

That is small enough to write as one file: an HTTP handler that calls Binance, runs some SQL, and returns JSON. Many systems start exactly there.

The problem with the one-file version. Binance's pagination rules, its rate limits, and DuckDB's SQL end up woven through the logic that decides what "missing" means. Swap Binance for another exchange, or DuckDB for Postgres, and you are editing the rules too. Testing "what is a gap?" needs a network and a database.

So the organising question for everything that follows is:

How do we arrange this so that Binance and DuckDB are replaceable — without their details leaking into the parts that decide what the data means?

The answer is built up one layer at a time, starting from the smallest thing: the words the system uses. The diagram on the right is empty on purpose. It fills in as you go, and nothing appears in it before it has been explained.

The one running example

Every chapter reuses the same scenario, so you only have to hold one story in your head:

Get every 1-minute Bar of  binance / BTCUSDT / 1m
for                         [2024-01-01, 2024-01-02)
then tell me whether that range can be trusted.

02 · Domain · Range

Range — the shape of time

Almost every question in this system is about a span of time. So the first thing to pin down is what a span is.

A Range is half-open: it includes its start and excludes its end.

[10:00, 10:05) at 1m 10:00 ✓ 10:01 ✓ 10:02 ✓ 10:03 ✓ 10:04 ✓ 10:05 ✗ (excluded)

Why half-open?

Because then ranges tile without overlapping or leaving holes. [10:00, 10:05) followed by [10:05, 10:10) is exactly ten Bars, and nobody has to argue about who owns 10:05. A 1m Bar that opens at 10:04 belongs to [10:00, 10:05); the one that opens at 10:05 does not. Coverage, Gaps, Backfill requests and Binance pages all use this one convention, so they can be compared directly.

What can you do with two Ranges?

Once the basic idea is clear, the operations are just set arithmetic on time:

OperationMeaningExample
Overlapsshare at least one instant[0,2) vs [1,3) → yes; [0,2) vs [2,4) → no (adjacent)
Touchesone ends exactly where the other starts[0,2) vs [2,4) → yes
Unionmerge into one, if they overlap or touch[0,2) ∪ [2,4) = [0,4)
Intersectthe part in both[0,3) ∩ [2,5) = [2,3)
Subtractremove one from the other; 0, 1 or 2 pieces[0,10) − [3,5) = [0,3), [5,10)

Two helpers work on lists: MergeRanges sorts and coalesces, SubtractRanges removes many from many. You will meet them again in IsComplete: "is the requested range inside Coverage?" is literally SubtractRanges([r], coverage) being empty.

AgnoForgeAll bounds are UTC. The zero Range is empty. An empty Range contains, overlaps and touches nothing. internal/acquisition/domain/range.go
Show me the code
// Range is a half-open span [Start, End) over Bar open_time, in UTC.
type Range struct { Start, End time.Time }

func (r Range) Overlaps(other Range) bool {
    if r.IsEmpty() || other.IsEmpty() { return false }
    return r.Start.Before(other.End) && other.Start.Before(r.End)
}

03 · Domain · Bar

Bar — one piece of market data

The unit the whole system moves around.

A Bar summarises one Timeframe of trading — for 1m, sixty seconds — as five numbers plus the moment it opened:

OpenTime  2024-01-01T00:00:00Z
Open      42283.58
High      42298.62
Low       42261.02
Close     42265.02
Volume    42.75513000

Two deliberate choices

Prices are strings, not floats. This service's job is to keep what the provider said, exactly. 42283.58 as a float64 is 42283.580000000001…; as a decimal string it is 42283.58 forever. Storage uses DECIMAL(20,8) for the same reason.

Only closed Bars exist. The candle that is still forming right now is never a Bar. That rule shows up later as "clip the end of the requested range down to the last closed Bar".

Validation lives here, not in the adapter

Whether a Bar is usable is a domain question — the answer does not depend on which exchange it came from. Bar.Validate() checks: open time is non-zero and UTC; every price parses as a decimal and is > 0; volume is ≥ 0; Low ≤ min(Open, Close) and High ≥ max(Open, Close). The Binance adapter calls this and drops what fails; it does not get to decide the rule.

AgnoForgeinternal/acquisition/domain/bar.go. Prices are compared with math/big.Rat, so validation is exact too.
Show me the code
type Bar struct {
    OpenTime time.Time
    Open, High, Low, Close, Volume string   // decimal strings, never floats
}
func (b Bar) Validate() error { /* zero/UTC check, decimal parse, low/high vs body */ }

04 · Domain · DatasetID, Timeframe

Dataset — which market data?

Bars are meaningless without knowing whose Bars, of what, at what resolution.

A DatasetID is three parts, and it is spelled the same way in URLs, logs and the database:

Provider  +  Symbol   +  Timeframe
binance   /  BTCUSDT  /  1m
  • Provider — who served the Bars. Just a name ("binance") at this layer; the domain has no idea what a Binance is.
  • Symbol — the market, spelled exactly as the provider spells it. BTCUSDT, not BTC/USD. The domain deliberately does not normalise it.
  • Timeframe — the duration of one Bar.

One DatasetID names one source dataset. Bars from Binance and Bars from another exchange for the same pair are two different Datasets, never merged here — merging is another module's job.

Timeframe — the tick of the clock

A Timeframe is a fixed duration with a canonical short name: 1m 3m 5m 15m 30m 1h 2h 4h 6h 8h 12h 1d 3d. That is the closed list; ParseTimeframe rejects anything else.

Why no 1w or 1M? Because a month is not a fixed number of milliseconds. Every Timeframe here can be aligned to a boundary by arithmetic from the Unix epoch — and the next two pages depend on that being possible.
AgnoForgeinternal/acquisition/domain/dataset.go, internal/acquisition/domain/timeframe.go. Timeframe.Duration() is the only place the list of durations lives.
Show me the code
type DatasetID struct {
    Provider  string
    Symbol    Symbol      // "BTCUSDT"
    Timeframe Timeframe   // "1m"
}
func (d DatasetID) String() string { return d.Provider + "/" + string(d.Symbol) + "/" + string(d.Timeframe) }

05 · Domain · Gap

Gap — what is missing?

The system's whole reason to exist is to know when data is missing. That idea needs a name.

Expected Present Gap 10:00 10:00 10:01 10:01 10:02 — ┐ 10:03 — ┘ [10:02, 10:04) 10:04 10:04

A Gap is a contiguous Range where Bars are expected but absent. Two adjacent missing minutes are one Gap, not two. Note the Gap's end is 10:04, half-open, like every other Range.

A Gap is a record, not just a fact

Once found, a Gap is stored with an id, and it has a lifecycle, because humans need to make decisions about missing data:

StatusMeaningBlocks "trusted"?
openexpected, still absent, nobody has decided anythingyes
repairedthe Bars turned up (a Repair, or any later Backfill)no
ignoredan operator accepted the absenceno
unrecoverablethe provider will never serve those Barsno

ignored and unrecoverable are called settled: someone has decided. Only open stands in the way of a range being Complete. And repaired is special: an operator may never set it by hand — only the detector, by observing the Bars, gets to say so.

AgnoForgeinternal/acquisition/domain/gap.go. Gap{ID, Dataset, Range, Status, Reason}. ParseGapStatus accepts exactly the four names.
Show me the code
const (
    GapOpen          GapStatus = "open"
    GapRepaired      GapStatus = "repaired"
    GapIgnored       GapStatus = "ignored"
    GapUnrecoverable GapStatus = "unrecoverable"
)
type Gap struct { ID int64; Dataset DatasetID; Range Range; Status GapStatus; Reason string }

06 · Domain · TradingCalendar

Trading Calendar — what should exist?

"Missing" only makes sense against "expected". Who says what is expected?

Look back at the Gap example. It said expected: 10:00, 10:01, 10:02…. That list did not come from nowhere. For a crypto exchange trading 24/7 every minute is expected. For a stock exchange, Saturday is not missing — it was never supposed to be there.

ConceptGap detection is expected − present. The Trading Calendar supplies "expected". A market-closed period the calendar omits is not a Gap, and does not even break a Gap into two.

So the domain defines the calendar as a question, and lets each provider answer it:

type TradingCalendar interface {
    // every open_time in [r.Start, r.End) that falls on a tf boundary, ascending
    Expected(r Range, tf Timeframe) iter.Seq[time.Time]
}

The domain ships one answer, because it is universal: Continuous{}, the 24/7 calendar. Every Timeframe boundary in the range is expected. Boundaries are multiples of the Timeframe measured from the Unix epoch — which is why Timeframes had to be fixed durations.

Continuous.Expected([00:00:30, 00:03:00), 1m)
  → 00:01, 00:02          // start aligned UP to the next boundary; end excluded
AgnoForgeinternal/acquisition/domain/calendar.go. Binance's adapter returns domain.Continuous{} from its Calendar() method. A future stock-market provider would return its own.

This is the first place you have seen an interface in this walkthrough. Hold that thought: an interface is "a question the caller asks, that somebody else answers". Chapter 3 is entirely about that idea.

You now own the vocabulary

Range, Bar, DatasetID, Timeframe, Gap, Calendar. Nothing so far has downloaded, stored, or served anything. Now we can ask what the system does.

07 · The application layer

The Application — what can the system do?

The domain is nouns. The application is verbs.

ConceptThe application layer holds the use cases: the things a user can ask the system to do. Each use case orchestrates domain objects to get a job done. It knows what has to happen and in what order — but not how the outside world is reached.

Watch the diagram: a second box has appeared around the domain. That is the spatial rule for this whole walkthrough — new layers wrap the old ones. The application can see and use everything in the domain; the domain cannot see the application.

08 · Use case

StartBackfill

"Get Binance BTCUSDT 1m from Jan 1 to Feb 1."

Input
BackfillRequest{Provider, Symbol, Timeframe, Range}
Domain used
DatasetID, Timeframe, Range, Bar
Needs from outside
market data for a Symbol over a Range · storage for Bars and Coverage
Result
BackfillStatus — immediately, with the effective range; the work continues in the background

What the application is responsible for

  1. Validate. Is the Provider one we were built with? Does it support this Timeframe? Does it know this Symbol? Each "no" is a permanent error; nothing is started.
  2. Determine the effective range. Clip the start up to the earliest Bar the provider has, and the end down to the last fully closed Bar (the forming candle is never a Bar — remember?). If nothing remains, ErrEmptyRange.
  3. Refuse a duplicate. One running Backfill per Dataset: ErrBackfillRunning otherwise.
  4. Register and return. The caller gets an id and the effective range straight away.
  5. In the background, page by page: ask for Bars → persist the page → extend Coverage by exactly that page. Coverage is only ever extended over Bars that are already stored, so it never claims what is not there.
  6. Terminal work (even after a cancel): on completion, extend Coverage to the whole effective range — the instants the provider had no Bar for become Gaps — then run DetectGaps over it.

Notice what is not here

Nowhere in that list is a URL, a rate limit, a SQL statement, or a JSON field. The application says "give me Bars for this range" and "store these" — and deliberately does not say how. That is a promise we still have to make good on, in Chapter 3.

AgnoForgeinternal/acquisition/app/backfill.go — Service.StartBackfill, Service.run, Service.Backfill, Service.CancelBackfill, Service.Wait. The registry of running Backfills is in memory (// ponytail: in-memory registry); it does not survive a restart.

09 · Use case

DetectGaps

"Inside what I asked for, what is missing?"

Input
DatasetID, Range
Domain used
TradingCalendar (expected), Range arithmetic, Gap, GapStatus
Needs from outside
the provider's Calendar · from storage: Coverage, the open_times present, the existing Gaps; and a way to write Gaps back
Result
the open Gaps the Dataset now has in the range

The algorithm, in the domain's words

for each piece of Coverage that r intersects:
    expected = Calendar.Expected(piece, timeframe)
    present  = open_times stored in piece
    settled  = ranges of Gaps an operator marked ignored / unrecoverable
    missing  = expected − present − settled
    one Gap per run of consecutive missing open_times
replace the open Gaps in r with what was found

Three rules that fall out of the domain:

  • Only Coverage can be judged. A range never asked for is unknown, not missing — no Gap is recorded outside Coverage.
  • "Consecutive" is in the calendar's sequence. A market-closed period neither becomes a Gap nor splits one.
  • Detection heals first. Any Gap the range touches whose Bars are now all present becomes repaired — whatever status it was in. This is how a Repair closes its own Gap, and how an ignored Gap whose data later appears gets corrected.
AgnoForgeinternal/acquisition/app/gaps.go — Service.DetectGaps, with helpers settleGaps, isFilled, openTimes. It runs automatically at the end of every Backfill, and is not exposed as its own HTTP route.

10 · Use cases

IsComplete, Repair, Query

The remaining three verbs are short — and they show how much of the work the domain already did.

IsComplete — "can I trust this range?"

This is the only question another service should ask before using data. The answer is two checks, both pure Range arithmetic over stored facts:

covered = SubtractRanges([r], Coverage) is empty      // r ⊆ Coverage
blocked = any Gap with status=open intersecting r
Complete = covered && !blocked                        // plus: the blocking Gaps, so the caller knows why

An empty range is trivially Complete. Settled and repaired Gaps do not block.

Repair — "try to fill that Gap"

A Repair is just a Backfill over exactly the Gap's Range, in the Gap's Dataset. It reuses StartBackfill entirely. It does not touch the Gap's status: the Backfill's terminal DetectGaps runs over the Gap's range, sees the Bars are present, and marks it repaired on its own. Alongside it, SetGapStatus lets an operator set open, ignored or unrecoverable with a reason — never repaired.

Query — the read side

Coverage, Gaps, Bars, ExportParquet. These are pass-throughs to storage, and they never refuse an incomplete range — that is what IsComplete is for. They exist on the Service for one architectural reason, stated in the code: "so an inbound adapter depends on the use cases alone and never on the Store."

AgnoForgeinternal/acquisition/app/complete.go, repair.go, query.go.

The application layer is done — but it has a hole in it

11 · Why ports exist

The application needs help

Two honest questions, and the architecture falls out of the answers.

StartBackfill needs Bars. Should StartBackfill know how Binance HTTP works — the /api/v3/klines path, 1000-row pages, the 6000-weight-per-minute budget, what a 429 means?

No. The moment it does, adding a second exchange means editing the backfill logic, and testing the backfill logic means talking to Binance.
StartBackfill needs to store Bars. Should it know DuckDB SQL — INSERT OR REPLACE, the bars table, epoch-millisecond columns?

No. Same reason.

So what does the application do instead?

It writes down, in its own vocabulary, exactly what it needs — and nothing about how:

I need something that can:
  · tell me its name and which Timeframes it offers
  · tell me the earliest Bar it has for a Symbol
  · give me its Trading Calendar for a Symbol
  · give me the Bars of a Symbol over a Range, page by page, in order

I need something that can:
  · store Bars for a Dataset (again and again, same result)
  · extend and read a Dataset's Coverage
  · list the open_times present in a Range
  · store, list, read and update Gaps
  · read Bars back, and export them as Parquet
ConceptEach list is a port: a contract, written and owned by the application, describing a capability it requires from the outside world. In Go a port is an interface. The application depends on the interface; something outside, later, will satisfy it. This flip — the inner layer defines the contract, the outer layer conforms to it — is dependency inversion, and it is the whole trick of the hexagonal style.

The diagram shows the two contracts as sockets on the edge of the application: one for market data, one for storage. Nothing is plugged into them yet. That is the point.

AgnoForgeBoth ports live in one file, internal/acquisition/app/ports.go, named app.Provider and app.Store. The next two pages read them.

12 · Port

Provider — the market-data contract

The application: "I need Bars." The port: "Here is what 'give me Bars' means."

type Provider interface {
    Name() string                                      // "binance" — first part of a DatasetID
    SupportedTimeframes() []domain.Timeframe
    EarliestAvailable(ctx, s domain.Symbol) (time.Time, error)
    Calendar(s domain.Symbol) domain.TradingCalendar
    Bars(ctx, s domain.Symbol, tf domain.Timeframe, r domain.Range) iter.Seq2[[]domain.Bar, error]
}

Read the vocabulary: Symbol, Timeframe, Range, Bar, TradingCalendar. All domain types. Nothing on this interface is specific to any exchange — that is the test of a well-drawn port.

The contract says more than the signatures

The doc comments are part of the port. Bars must: yield in ascending open_time, page by page, with no Bar repeated or skipped; clip the start up to EarliestAvailable and the end down to the last closed Bar; drop Bars that fail domain.Bar.Validate; yield a failure once, then stop; and refuse an unsupported Timeframe without contacting anyone. Every implementer owes all of that, so the application can rely on it.

Errors cross the boundary as domain sentinels

An unknown symbol is domain.ErrUnknownSymbol; an unsupported timeframe is domain.ErrUnsupportedTimeframe. Adapters wrap these; the application branches on them with errors.Is and never sees an HTTP status.

Who owns it
the application (internal/acquisition/app)
Who calls it
StartBackfill (EarliestAvailable, Bars), DetectGaps (Calendar), Providers listing
Who implements it
someone outside — Chapter 4
AgnoForgeinternal/acquisition/app/ports.go. The Service is built with a list of Providers keyed by Name(); an unknown name is app.ErrUnknownProvider. Adding a second exchange means adding one more element to that list.

13 · Port

Store — the persistence contract

The application: "I need these kept." The port: "Here is what 'kept' means."

type Store interface {
    UpsertBars(ctx, id domain.DatasetID, bars []domain.Bar) error        // idempotent
    ExtendCoverage(ctx, id domain.DatasetID, r domain.Range) error       // union-merges
    Coverage(ctx, id domain.DatasetID) ([]domain.Range, error)          // sorted, coalesced
    OpenTimes(ctx, id domain.DatasetID, r domain.Range) iter.Seq2[time.Time, error]
    ReplaceOpenGaps(ctx, id domain.DatasetID, r domain.Range, gaps []domain.Gap) error
    Gaps(ctx, id domain.DatasetID, f GapFilter) ([]domain.Gap, error)
    Gap(ctx, gapID int64) (domain.Gap, error)
    SetGapStatus(ctx, gapID int64, s domain.GapStatus, reason string) error
    Bars(ctx, id domain.DatasetID, r domain.Range) ([]domain.Bar, error)
    ExportParquet(ctx, id domain.DatasetID, r domain.Range, w io.Writer) error
}

Again: DatasetID, Range, Bar, Gap, GapStatus. No table names, no SQL, no connection strings. Ranges are half-open on open_time, like everywhere else.

Contract details the use cases lean on

  • UpsertBars is idempotent: a Backfill or Repair run twice changes nothing. That single guarantee is what lets Repair be "just a Backfill".
  • ExtendCoverage union-merges with what is already recorded, so touching ranges become one — Range.Union, at the storage boundary.
  • ReplaceOpenGaps touches only open Gaps inside the range. Settled Gaps and Gaps outside are left alone — DetectGaps depends on exactly that.
  • A missing Gap is domain.ErrNotFound, wrapped.
ConceptProvider and Store are both outbound (or "driven") ports: the application calls out through them. The other direction — something calling in to the application — is discussed on the HTTP page, because AgnoForge handles it differently, and honestly.
AgnoForgeinternal/acquisition/app/ports.go. GapFilter{Status *GapStatus, Range *Range} lives next to it: nil means "no constraint".

14 · Outbound adapter

Binance — implements Provider

Now, and only now, an exchange enters the picture.

ConceptAn adapter is the piece that makes a specific technology satisfy a port. It knows the port's vocabulary (domain types) on one side and the technology's quirks on the other, and it translates. Adapters depend on the application; the application never depends on an adapter.
app.Provider  ◄── implements ──  binance.Provider

// in the adapter, at compile time:
var _ app.Provider = (*Provider)(nil)

What stops here

Everything Binance-specific — and nothing else:

Pagination1000 klines per request; walks forward in pages, clipped to the effective range

16 · Inbound adapter

What it is responsible for

Routing; parsing path, query and JSON bodies into domain values (ParseTimeframe, parseRange); JSON responses; and turning errors into status codes — ErrNotFound → 404, ErrBackfillRunning → 409, permanent validation errors → 400.

What it must not contain

No market-data rules, no Gap rules, no backfill logic, no Binance, no SQL. If you find yourself computing anything about Ranges in a handler, it belongs one layer in.

AgnoForgeHonest note on inbound ports. Some hexagonal codebases define an explicit inbound port interface (a "driving port") that the HTTP adapter depends on. AgnoForge does not. httpapi.New takes a concrete *app.Service, and the Service's methods are the application API. The outbound side has explicit interfaces because there are real alternatives to swap (fake Provider, in-memory DuckDB); the inbound side has one caller and no need for the seam yet. The asymmetry is deliberate, not an oversight — and this page would be lying if it drew a port there.
AgnoForgeinternal/acquisition/adapters/httpapi/ — api.go (mux, error mapping, parsing), backfills.go, datasets.go, gaps.go, wire.go (JSON shapes). A second inbound adapter, internal/acquisition/adapters/playground, serves the tracing UI on the same mux; it is not part of the teaching path here.

17 · Assembly

Composition Root — who plugs it all together?

The application does not know DuckDB. It does not know Binance. The HTTP adapter does not know either. So who does?

ConceptThe composition root is the one place where abstractions meet concrete implementations: it constructs the adapters, hands them to the application, hands the application to the inbound adapter, and starts serving. It is the only code allowed to know everything — and it does nothing else.
AgnoForgecmd/agnoforge, function serveOn in serve.go. Its comment: "this function is the one place in the program where a concrete Store and a concrete Provider are named."
store    := duckdb.Open(cfg.DBPath)                              // a Store
provider := binance.New(cfg.BinanceBaseURL, &http.Client{…})     // a Provider
svc      := app.New(store, []app.Provider{provider})             // use cases over the ports

mux := http.NewServeMux()
mux.Handle("/", httpapi.New(svc, logger))                        // inbound adapter over the use cases
server := &http.Server{Handler: mux}
server.Serve(listener)

Read the flow downward: concrete things are built first, then handed inward. app.New accepts app.Store and []app.Provider — the interfaces — so it receives a DuckDB Store and a Binance Provider without ever naming them.

On the diagram the composition root is a dashed outline around everything: it does not sit in any layer, it holds them.

Also here, because it is wiring, not logic

  • Configuration from the environment: AGNOFORGE_DB_PATH, AGNOFORGE_LISTEN, BINANCE_BASE_URL.
  • Graceful shutdown ordering: stop accepting → cancel and await running Backfills (svc.Shutdown) → close the Store. The order matters; this is the only place that knows all three exist.
  • Tracing setup and the playground's routes (ADR-0003).
  • The sibling Composite Market Dataset context (internal/composite/) is wired in the same serveOn: its own Store, Service and routes on the same mux, consuming acquisition only through svc (ADR-0005). A separate explainer covers it; it is elided from the snippet above.

The agnoforge data … subcommands live in the same binary but are just HTTP clients of the API; they never touch the Service directly.

Now derive the rule

We did not start with a dependency rule; we built the pieces and can now read the rule off them:

domain  ←  app  ←  adapters  ←  cmd

Domain does not know Application.          (imports: stdlib only)
Application does not know Binance.         (it knows app.Provider)
Application does not know DuckDB.          (it knows app.Store)
Adapters know the interfaces they implement — and the domain.
cmd knows the concrete implementations, because it assembles them.

Every arrow points inward. Volatile things (exchanges, databases, transport) are outside; stable things (what a Bar is, what a Gap is) are inside. That is the entire reason the shape is what it is.

One note on scope: everything on this page lives under internal/acquisition/. A second bounded context, internal/composite/ (Composite Market Dataset), sits beside it with the same layered shape and consumes acquisition through a port of its own — see CONTEXT-MAP.md; it has its own explainer.

Quick self-check

Where does "parse the Binance rate-limit header" go?
Binance adapter. It is a Binance detail; no other layer may know it.
Where does "a Gap is repaired when all its Bars are present" go?
Application (DetectGaps / settleGaps). It is a rule about the use case, using domain vocabulary. Not the domain: it needs storage to answer.
Where does "two touching ranges are one range" go?
Domain (Range.Union, MergeRanges). True regardless of provider or store. The DuckDB adapter calls it.
Where does "map ErrBackfillRunning to 409" go?
HTTP adapter. Status codes are transport.
Where is duckdb.Open called in production?
Only in cmd/agnoforge/serve.go (serveOn).

19 · Runtime

Follow one Backfill through the architecture

Static structure is half the story. Click a step (or use the buttons) and watch it light up on the right.

  1. User → HTTPagnoforge data backfill binance BTCUSDT 1m 2024-01-01 2024-01-02 sends POST /backfills with a JSON body.
  2. HTTP → StartBackfillThe handler parses Timeframe and Range into domain values and calls svc.StartBackfill(ctx, BackfillRequest{…}).
  3. Application → Provider port → BinanceValidation: EarliestAvailable("BTCUSDT") goes out through app.Provider; the Binance adapter answers with one klines request. The effective range is computed.
  4. 202 AcceptedThe Backfill is registered and the response returns immediately with its id and effective range. The run continues in a goroutine with its own context.
  5. Application → Provider.Bars → BinanceBars(ctx, "BTCUSDT", "1m", eff). The adapter pages GET /api/v3/klines, 1000 at a time, within its rate budget, decoding and validating each kline into a domain.Bar.
  6. Application → Store port → DuckDB, per pageUpsertBars (INSERT OR REPLACE INTO bars …), then ExtendCoverage for exactly that page's range. Repeat from step 5 until the provider runs out of pages.
  7. Terminal work: DetectGapsCoverage is extended to the full effective range, then DetectGaps runs: Calendar.Expected − OpenTimes − settled → ReplaceOpenGaps. The Backfill becomes completed.
  8. Later: "can I trust it?"GET /datasets/binance/BTCUSDT/1m/complete?start=…&end=… → IsComplete → Coverage + Gaps(open, range) from the Store → {"complete": true}, or the open Gaps blocking it.

Notice the shape of every hop: adapter → application → port → adapter. Control passes through the centre on every trip, and the two adapters never meet.

20 · Runtime

Follow a Gap from detection to repair

Same scenario, one wrinkle: Binance had no Bars for [00:02, 00:04).

  1. DetectGaps asks the CalendarAt the end of the Backfill, the application asks the Binance adapter for its Calendar("BTCUSDT") — domain.Continuous{} — and iterates Expected(coverage piece, 1m): every minute.
  2. …and the Store what is presentOpenTimes(ds, piece) streams the stored open_times; Gaps(ds, settled) gives ranges to exclude. Expected − present − settled = 00:02, 00:03 → one Gap [00:02, 00:04).
  3. Record itReplaceOpenGaps(ds, range, [gap]): DuckDB deletes open gaps in range and inserts the new one, id 7, status open.
  4. An operator sees itGET /datasets/binance/BTCUSDT/1m/complete → complete: false, with Gap 7 listed. GET …/gaps?status=open shows the same.
  5. RepairPOST /gaps/7/repair → svc.Repair(7): load the Gap, then StartBackfill over exactly [00:02, 00:04). From here it is the previous trace again, on a tiny range.
  6. Fetch and store the two BarsBinance now has them. UpsertBars is idempotent, so nothing else in the table is disturbed.
  7. Terminal DetectGaps heals the GapsettleGaps finds Gap 7's range fully present → SetGapStatus(7, repaired). Nobody set it by hand; the detector observed the Bars.
  8. Or: the operator gives upIf Binance never serves them: PATCH /gaps/7 {"status":"unrecoverable","reason":"exchange outage"} → SetGapStatus. The Gap is settled, stops blocking Complete, and is excluded from "expected" on the next detection.

21 · Confidence

How the architecture makes testing easier

The boundaries you have been drawing are not just organisation. Every port is a place where a fake can be plugged in.

LayerHow it is testedWhat is real / what is fake
Domainpure table-driven testseverything real; no I/O exists to fake. internal/acquisition/domain/*_test.go
Applicationuse cases against a fake Provider and a real in-memory DuckDBfakeProvider implements app.Provider from a slice of Bars; duckdb.Open(":memory:") is the real Store. internal/acquisition/app/*_test.go
Binance adapteragainst an httptest.Server that speaks klinesreal adapter, fake exchange: pagination, rate limits and retries are all scripted. internal/acquisition/adapters/binance/harness_test.go
DuckDB adapteragainst :memory:real database, no disk. Includes a scale test. internal/acquisition/adapters/duckdb/*_test.go
HTTP adapterhttptest.NewServer(httpapi.New(svc, …))real handlers over a real Service built with a fake Provider and :memory: DuckDB. internal/acquisition/adapters/httpapi/harness_test.go
Compositionend-to-end: serveOn with a fake Binanceeverything real except the exchange, which is an httptest.Server reached through BINANCE_BASE_URL. cmd/agnoforge/e2e_test.go

Read the pattern

Each fake sits exactly at a port or at the process edge:

fake Provider        ──  at app.Provider          (application tests, HTTP tests)
fake Binance server  ──  at the network edge      (adapter tests, e2e)
:memory: DuckDB      ──  at app.Store, but real    (the adapter is cheap enough to keep)
httptest             ──  at the inbound edge

The Binance adapter takes its base URL as a constructor argument for one reason: so a test can hand it a fake server. That is dependency injection at the adapter's own outer edge — the same idea as the ports, one layer further out.

The claim, stated plainly: the only tests that need the network are none. The only tests that need a file on disk are none. And "what is a Gap?" is tested with zero I/O.
