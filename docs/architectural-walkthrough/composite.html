00 · Before architecture

Why does this exist?

A researcher wants to backtest against one continuous BTC/USD price history. What actually exists is messier.

  1. The bars live per provider: Binance has BTCUSDT 1-minute bars from some date, Coinbase has BTC-USD bars over a different span. Neither alone covers the range the researcher wants.
  2. The stored history has holes — exchange outages, ranges never downloaded — and it stops wherever the last download stopped, not at "now".
  3. The backtester wants 1-hour or 1-day bars over an exact date range, as one clean file. It does not want to know any of the above.
The problem with the naive version. Copy everyone's bars into one big table, prefer whichever provider "looks better" where they overlap, resample on the fly, and hand the result over. Now nobody can answer: where did this bar come from? Which stretches are actually missing? Did two providers disagree at the seam, and by how much? A dataset that hides its own defects is worse than no dataset — a backtest against it produces confident nonsense.
How do we arrange this so that where the data is stored and how it is acquired stay replaceable — without those details leaking into the rules that decide what a composite timeline is, when it is trustworthy, and what it must never hide?

The one running example

Every chapter reuses this single dataset. It exercises everything: two providers, a live end, materialized frames, an honest quality report.

composite dataset  btc-research
  instrument   BTC/USD
  base         binance:BTCUSDT · 1m
  catch-up     kind=source → coinbase:BTC-USD · 1m
  range        2024-01-01 → now
  timeframes   1h, 1d          # materialized on build
  mode         research        # ready even with flagged imperfections

01 · The core

Start with the domain

Before any database or HTTP route: what does this system fundamentally talk about?

ConceptThe core (domain) layer holds the vocabulary and the rules that would still be true if you rewrote every technical detail around it. It should be testable with nothing but values in memory.
AgnoForgeLives in internal/composite/domain/. Its package doc says exactly what it may depend on: the standard library, and the acquisition domain for the terms that context owns — Range, Symbol — used with acquisition's meaning. It knows nothing about storage, HTTP, or the acquisition application service.
Honest note. A textbook core imports only the standard library. This one deliberately imports a second domain package (acq "…/internal/acquisition/domain"). That is a documented context relationship (CONTEXT-MAP.md), not an accident: a half-open Range and a provider Symbol mean the same thing in both contexts, and restating them would let the two drift apart. The line it never crosses is the acquisition application — the core imports acquisition's words, never its behaviour.
What it knows
What a Composite Dataset is: its Name, Instrument, Config, lifecycle State, Segments, Transitions, Quality, calendar-aware Timeframes, and the rules over them (validation, readiness vocabulary, window arithmetic).
What it must NOT know
DuckDB, SQL, HTTP, JSON, Binance/Coinbase APIs, how a backfill runs, where bars are stored.
Who calls it
The application layer (composite/app) and, for translation only, the adapters.
What it calls
Standard library + acquisition domain types. Nothing else — no interfaces, no I/O.

02 · Domain · Name & Instrument

Name & Instrument — identity and meaning

Two tiny validated strings that carry the two biggest promises in the model.

ParseName("btc-research") ✓ Name ParseName("BTC Research!") ✗ ErrInvalidConfig — not a kebab-case slug ParseName("btc@2") ✗ "@" is reserved for a future name@version ParseInstrument("BTC/USD") ✓ Instrument

Why?

Name is the primary key of the whole context: every route, every table row, every log line addresses a dataset by it. The parser rejects @ on purpose — the model reserves room for a later name@version identity, so the character cannot be taken by accident today.

Instrument is the anti-goof rule for cross-provider assembly. Binance calls the market BTCUSDT, Coinbase calls it BTC-USD. There is no registry and no symbol mapping: the Instrument is the user's assertion that those provider symbols really are the same market, and Config.Validate refuses any source that declares a different one.

AgnoForgedomain/name.go, domain/instrument.go. Both parse-don't-validate: you cannot construct an invalid one through the parser, and both refusals wrap ErrInvalidConfig.
Show me the code
// Name is the identity of a Composite Dataset: a kebab-case slug, unique
// across the context. It is the primary key, and it deliberately leaves room
// for a later `name@version` identity — which is why "@" is not a legal
// character in one.
type Name string

func ParseName(s string) (Name, error) {
    if !isSlug(s) || len(s) > maxNameLength {
        return "", fmt.Errorf("%w: name %q is not a kebab-case slug", ErrInvalidConfig, s)
    }
    return Name(s), nil
}

03 · Domain · Timeframe

Timeframe — why this context grew its own

Nine canonical frames: 1m 5m 15m 30m 1h 4h 1d are fixed-length; 1w and 1M follow the calendar. The calendar frames are the whole reason this type exists (ADR-0004).

acquisition Timeframe: fixed only — a bar boundary is N × duration from the Unix epoch composite Timeframe: the same seven, plus 1w and 1M 1w window start: Monday 00:00 UTC (ISO-8601) — NOT "7d from epoch": the epoch is a Thursday 1M window start: the 1st, 00:00 UTC — 28/29/30/31 days long

Why not extend acquisition's Timeframe?

Acquisition's alignment is integer arithmetic from the epoch — a correct, simple invariant for fixed frames that a variable-length week would break. So acquisition keeps its constraint, and the composite context defines its own Timeframe with calendar-aware boundary arithmetic in calendar.go: WindowStart, Window (half-open), and WindowStarts (an iterator over every window overlapping a range).

One map, acquisitionFrames, is deliberately the only bridge between the two vocabularies. The calendar frames have no entry, so tf.Acquisition() reports false for them — there is no way to smuggle a 1w across the port boundary. The same map is where the fixed frames get their Duration(): taken from acquisition rather than restated, so the two contexts cannot drift about how long a 4h bar is.

AgnoForgedomain/timeframe.go (identity, order, the bridge) and domain/calendar.go (boundary arithmetic, all UTC, no timezone configuration — "and never will in v1").
Show me the code
func (tf Timeframe) WindowStart(t time.Time) time.Time {
    u := t.UTC()
    switch tf {
    case TF1w:
        // ISO-8601: Monday is day 0 of the week.
        day := time.Date(u.Year(), u.Month(), u.Day(), 0, 0, 0, 0, time.UTC)
        return day.AddDate(0, 0, -((int(day.Weekday())+6)%7))
    case TF1M:
        return time.Date(u.Year(), u.Month(), 1, 0, 0, 0, 0, time.UTC)
    }
    step := tf.Duration().Milliseconds()
    if step <= 0 { return time.Time{} }
    return time.UnixMilli(alignDown(u.UnixMilli(), step)).UTC()
}

04 · Domain · Dataset

Dataset — a declaration with a lifecycle

A Composite Dataset is not data. It is a declaration (Config) plus where it is in its life (State).

Config of btc-research Instrument BTC/USD Base binance/BTCUSDT/1m must be a 1m source — validated CatchUp {source, coinbase/BTC-USD/1m} RequestedStart 2024-01-01T00:00:00Z RequestedEnd now re-resolved by every Build Timeframes [1h, 1d] 1m itself is refused here Mode research State: draft → building → ready | failed (+ stale)

The rules a researcher can get wrong on paper

Config.Validate refuses: a malformed Instrument; a base or catch-up source that is not 1m or declares a different Instrument; a fixed end not after the start; materializing an unknown frame or 1m itself ("the composite timeline itself, not a materialized timeframe"). Normalize makes two spellings of the same declaration identical — timeframes sorted and deduplicated, instants in UTC.

RequestedEnd is either a fixed instant or the literal now. Resolve(now) turns now into TF1m.WindowStart(now) — the open of the still-forming minute, i.e. the close of the last fully closed 1-minute bar. Everything a Build judges is judged against that Resolved End.

The lifecycle is three tiny functions

State.BeginBuild() — every resting state may rebuild; a dataset already building is refused with ErrBuildRunning. Settled(ready) — ready or failed. State.AfterEdit() — a built dataset becomes stale (only an edit causes staleness; source-data drift does not); a draft stays a draft.

AgnoForgedomain/dataset.go. One more derived rule lives here: Dataset.Observed() — a ready dataset whose bars were derived by an older MaterializationVersion reads as stale. Derived, never written: bumping the version marks every older dataset at once.
Show me the code
func (s State) BeginBuild() (State, error) {
    if s == StateBuilding {
        return "", fmt.Errorf("%w: a build of this composite dataset is already running", ErrBuildRunning)
    }
    return StateBuilding, nil
}

func (e RequestedEnd) Resolve(now time.Time) time.Time {
    if !e.Now { return e.At.UTC() }
    return TF1m.WindowStart(now)
}

05 · Domain · Segment

Segment — the provenance record

A contiguous, provider-attributed slice of the composite timeline. The ordered Segment list is the answer to "where did this bar come from?"

btc-research after a build (2 segments): [2024-01-01 ─────────────────── 2026-06-01) base binance/BTCUSDT/1m [2026-06-01 ───── resolved end) catch_up coinbase/BTC-USD/1m ↑ segments abut exactly: half-open, no overlap, no hole

Metadata, never a copy

A Segment holds a Kind, a Source, and a half-open Range — nothing else. It is metadata over source bars, never a copy of them (ADR-0005): the Range says which instants of the composite timeline this Source answers for. To attribute a bar, locate its open time in the list.

The Kind set is closed: base, catch_up, and live — which is reserved and never assembled in v1. It exists so adding live continuation later extends this model instead of reworking it.

AgnoForgedomain/segment.go. Segments are build output: the application computes them, the store replaces them wholesale on every build.

06 · Domain · Transition

Transition — the seam this context refuses to hide

The instant the timeline stops answering with one provider's data and starts answering with another's.

at 2026-06-01T00:00:00Z binance close (last bar before) : 67012.34000000 coinbase open (first bar at) : 67015.10000000 delta : +2.76000000 recorded, never enforced

Two functions, one honesty rule

TransitionsOf(segments) finds each boundary between segments of different sources (two adjacent segments of the same source are one stretch, not a transition). ValidateTransitions is the rule that makes a composite timeline one timeline. It refuses, wrapping ErrTransitionInvalid:

  • an overlap — two sources holding data for the same range. The one merge policy is reject_conflict: conflicting provider data is surfaced, never merged by guesswork;
  • a hole — a stretch no Segment answers for;
  • a different Instrument or canonical timeframe across the boundary — which would splice two markets, or two resolutions, into one timeline.

The price movement across a valid seam is recorded in Quality as three exact decimal strings (Close, Open, Delta) — never floats. The domain computes no prices at all: a price is a fact in acquisition's bars table, so TransitionsOf leaves them empty and the store fills them in. No threshold makes a delta a failure: it is evidence for the researcher, not a rule.

AgnoForgedomain/transition.go. Error messages name the policy in full, e.g. "reject_conflict refuses overlapping source data rather than merging it".
Show me the code
switch {
case next.Range.Start.Before(prev.Range.End):   // overlap
    return fmt.Errorf("%w: %s and %s both supply %s — reject_conflict refuses …", …)
case next.Range.Start.After(prev.Range.End):    // hole
    return fmt.Errorf("%w: nothing supplies %s between %s and %s — the segments must abut exactly", …)
}

07 · Domain · Quality

Quality — what a Build learned, kept honest

Enough for a researcher to judge fitness before running anything, and to explain afterwards what that build actually used. Every judgement is made against the Resolved End.

quality of btc-research requested 2024-01-01 → now resolved end 2026-08-31T12:59:00Z available 2024-01-01 → resolved expected 1,401,xxx bars · actual 1,400,9xx coverage 99.99% open gaps 1 [2025-03-02T04:10 … 04:25) transitions 1 (binance → coinbase, delta +2.76) incomplete 1h × 1 the window holding that gap mode research → ready anyway, imperfections listed (strict would have refused: failed, gaps named in the error)

Three honesty mechanisms

Gaps. A composite Gap keeps acquisition's own ID, so a repair can name the exact Gap acquisition knows.

Incomplete windows (materialization.go). A materialized window that emits a bar the source data does not fully back — an open Gap or an unsupplied stretch falls inside it — is flagged, never hidden and never silently dropped. Three rules: a window with no source bar at all emits nothing (not incomplete — just not materialized); a window that emits a bar over a hole is incomplete; the part of a window outside the resolved range is not missing data, because the dataset was never asked for it.

Mode. Quality.Strict() is the one boolean separating a strict dataset from a research one. Strict refuses readiness while any open Gap, unsupplied stretch, or incomplete window exists; research becomes ready with them listed and visibly flagged.

MaterializationVersion (currently 1) stamps every derived bar and the dataset row. Bump it only when the service would derive a different bar from the same source data — it is not a schema version.

The query rules live beside this in query.go: Dataset.Serves(tf) — only 1m and the declared frames are servable, anything else is ErrTimeframeNotMaterialized naming the frames that do exist, never an empty result; Dataset.QueryRange(start, end) — an omitted bound defaults to the dataset's own requested start / resolved end, and an empty range is refused rather than answered with no bars.

AgnoForgedomain/quality.go · materialization.go · query.go. Coverage is computed (ActualBars/ExpectedBars, two decimals), never stored.

09 · Use cases · declaration

Create, Edit, Delete — declaring is not building

A new dataset is a draft: declaring one builds nothing.

Intention
Let a researcher declare (and re-declare) what a composite dataset should be, without touching any data.
Inputs
A Name and a Config (Create/Edit); a Name (Dataset/Delete); nothing (Datasets).
Domain used
ParseName, Config.Normalize + Validate, State.AfterEdit, Dataset.Observed.
Needs from outside
Only the Store: create/read/update/delete declarations.
Result
The domain.Dataset as it now stands — Delete answers the declaration it removed.

Ordering that matters: both Create and Edit normalize and validate before anything is written, so a refused declaration leaves no trace. Edit moves a built dataset to stale — what is served no longer matches what is declared, and only the next Build reconciles them. Every read passes through Observed(), so a materialization-version mismatch reads as stale everywhere, consistently.

AgnoForgeapp/datasets.go. Duplicate names surface as domain.ErrDuplicateName from the Store — the Name is the identity, so there can only be one.

10 · Use cases · Build

Build — reconcile the declaration against reality

Synchronous and repeatable: rebuild is refresh. It leaves the dataset ready or failed, and either way the Quality is persisted so a failure is inspectable.

runBuild, in phase order (each phase = one child span): resolve now → last closed 1m bar; open the Quality ensure base coverage − resolved range = missing → backfill & wait (catchup.go) assemble base Segment + catch-up Segment for the tail the base could not supply validate ValidateTransitions — overlap/hole/mismatch fails the Build here judge per segment: Completeness → repair Gaps → count SourceBars; price Transitions; compute IncompleteWindows materialize derive declared frames in SQL — nothing if the mode refused readiness

The distinctions that make it honest

Shortfall vs failure. What a provider cannot supply — a head below its earliest-available floor, a tail nobody reaches — is a shortfall the mode judges (NotReady, an outcome). A port, backfill, or store that broke is a failure to run the Build at all, preserved as LastError.

Catch-up asks for the tail only. A configured catch-up provider is asked only for what the base genuinely could not supply — never to re-acquire history the base already has. If what it supplies reaches back into the base's range, validation refuses the overlap rather than quietly preferring one provider.

Two refusals from acquisition are absorbed, not surfaced (catchup.go · acquire): a backfill already running for the same source is waited out and retried (default: every 2s, 150 attempts — "five minutes of patience"); a provider with nothing in the range simply landed nothing. The researcher never sees either race.

Nothing derived outlives its build. A build that could not be ready saves no Segments and materializes nothing — earlier derived bars are removed with the Segments they came from.

AgnoForgeapp/build.go (~orchestration + phases), app/catchup.go (ensure, repair, acquire). View lives here too: Dataset + Segments + Quality, the whole provenance API.

11 · Use cases · bars

PlanBars, Bars, ExportBars — the consumer contract

The whole reason the context exists: a backtester asks for bars by name, Timeframe and range — and never learns which provider supplied which period, which gaps were repaired, or where anything is stored.

PlanBars resolves a request into a BarQuery and is the entire error contract of the query surface: unknown dataset → ErrNotFound; no timeline ever assembled → ErrNotBuilt; a frame the dataset does not serve → ErrTimeframeNotMaterialized; malformed frame or empty range → ErrInvalidConfig. A stale or research dataset is none of those: it answers, visibly as what it is.

The resolved BarQuery carries the dataset, the frame, the concrete range, and the ordered Segments. BarQuery.Derived() is the one decision point: 1m is read across the Segments from source bars; every other frame is read from materialized bars. Decided here and nowhere else — the consumer never has to ask.

Bars answers with exact decimal strings; ExportBars streams Parquet — "a year of bars is megabytes, and it never has to become Go values on the way out."

AgnoForgeapp/query.go. Omitted bounds default to the dataset's own requested start and resolved end, so "give me this dataset" needs no knowledge of what now resolved to.

12 · Why ports exist

The application needs help

Two dashed sockets just appeared under the application box. They are questions, not components yet.

Build needs source data to exist. Coverage, backfills, gap repair — that is Market Data Acquisition's whole job. Should the composite Build know how acquisition runs a backfill, or how Binance paginates? No. It should be able to ask, in its own words.
Every use case needs persistence. Declarations, segments, quality, derived bars. Should Create or PlanBars know that DuckDB is behind them, or what the tables are called? No.
ConceptA port is a contract owned by the inner layer, stated in the inner layer's vocabulary. The dependency arrow points inward — dependency inversion. The application compiles against the interface; something outside supplies the implementation.

Both interfaces live in one file the application owns: internal/composite/app/ports.go. Acquisition knows nothing about the port defined over it — it is consumer-defined.

13 · Port

AcquisitionPort — a control plane, and nothing else

Everything this context asks of Market Data Acquisition, in this context's own words. Note what is missing: there is no method that returns bars.

type AcquisitionPort interface {
    // Coverage returns the ranges the source Dataset has been acquired over.
    Coverage(ctx context.Context, src domain.Source) ([]acq.Range, error)

    // Completeness reports whether r can be trusted — covered, no open Gap —
    // and which open Gaps stand in the way.
    Completeness(ctx context.Context, src domain.Source, r acq.Range) (Completeness, error)

    StartBackfill(ctx context.Context, src domain.Source, r acq.Range) (BackfillHandle, error)
    WaitBackfill(ctx context.Context, h BackfillHandle) error
    DetectGaps(ctx context.Context, src domain.Source, r acq.Range) ([]domain.Gap, error)
    RepairGap(ctx context.Context, g domain.Gap) (BackfillHandle, error)
}

Two sentinels state, in composite words, the answers that are not failures: ErrBackfillBusy (a backfill of that source is already running — wait and ask again) and ErrNothingToAcquire (the provider's honest answer about what exists). The adapter translates whatever acquisition spells them as. BackfillHandle is an opaque string: only the adapter knows how acquisition names one.

Honest note — the deliberate bypass. Source 1-minute bars are the data plane, and they do not cross this port. They are read read-only, in SQL, from acquisition's own table through the Store port (ADR-0005): staging the largest data in the system through Go values would buy nothing. A future service split replaces one store read — not this port.

14 · Port

Store — persistence in domain vocabulary

Declarations, build output, derived bars, and the two reads of source data the bypass allows. It never writes source data — source Datasets belong to acquisition and are read-only here.

type Store interface {
    // declarations
    CreateDataset(ctx, d domain.Dataset) error          // duplicate name → ErrDuplicateName
    Dataset(ctx, name domain.Name) (domain.Dataset, error)
    Datasets(ctx) ([]domain.Dataset, error)
    UpdateDataset(ctx, d domain.Dataset) error
    DeleteDataset(ctx, name domain.Name) error          // removes everything derived, too

    // build output — replaced wholesale, in one go
    SaveBuild(ctx, d domain.Dataset, segments []domain.Segment, q domain.Quality) error
    Materialize(ctx, name domain.Name, m Materialization) (int64, error)
    Segments(ctx, name domain.Name) ([]domain.Segment, error)
    Quality(ctx, name domain.Name) (domain.Quality, bool, error)

    // the query surface
    Bars(ctx, q BarQuery) ([]acq.Bar, error)
    ExportBars(ctx, q BarQuery, w io.Writer) error       // Parquet, streamed

    // the accepted data plane (ADR-0005): read-only reads of acquisition's bars
    SourceBars(ctx, src domain.Source, r acq.Range) (SourceBars, error)
    TransitionDelta(ctx, from, to domain.Source, at time.Time) (PriceDelta, error)
}

The contract lines that matter: SaveBuild replaces Segments and Quality wholesale so what is stored always describes the build the row is in the state of; Materialize is the whole derived-data write — every frame not named is removed, and the empty Materialization (a failed build's) leaves no derived bars at all; Bars decides internally whether a query reads source bars or materialized ones, "and a consumer never sees the difference."

16 · Outbound adapter

DuckDB store — its own schema in the shared file

Implements Store on the same embedded DuckDB file acquisition uses. Sharing the file is the accepted data plane — not shared ownership of the schema.

Tech detailWhat stops here
Schema & migrationschema.go: six tables (composite_datasets, _segments, _quality, _quality_gaps, _quality_windows, _transitions, plus _materialized_bars), created idempotently on every Open; late columns arrive via ADD COLUMN IF NOT EXISTS. No statement writes to a table acquisition owns.
Exact pricesMaterialized bars are DECIMAL(20,8); transition prices are stored as the decimal strings they were computed as. TransitionDelta subtracts two decimals in SQL and casts only the result to text — no float anywhere on the path.
The aggregationmaterialize.go: one INSERT … SELECT per frame — arg_min("open"), max(high), min(low), arg_max("close"), sum(volume), grouped by a window expression that must agree with the domain's WindowStart for every instant (fixed frames: floored epoch arithmetic; 1w/1M: date_trunc). The store tests pin that agreement.
The two query pathsquery.go · barSource: a derived frame reads composite_materialized_bars; the 1m timeline is the Segments' source bars, clipped and UNION ALL-ed in timeline order. Parquet export is DuckDB's own COPY … TO.
AtomicitySaveBuild and Materialize each run in one transaction; segments and quality are delete-and-reinsert, wholesale.
Honest note. SourceBars, TransitionDelta, and the timeline/materialization SELECTs read acquisition's bars table directly — another context's table, read-only, by design (ADR-0005). This is the asymmetry the AcquisitionPort page promised: control plane through the port, data plane through the file.
AgnoForgeinternal/composite/adapters/duckdb/ — store.go, build.go, materialize.go, query.go, schema.go.

17 · Inbound adapter

httpapi — the REST resource that drives the application

Standard-library pattern mux, {"error": …} bodies, RFC3339 UTC instants — the acquisition adapter's conventions, so the two resources read as one API.

POST   /composites                  declare (draft) · 201, dup name → 409
GET    /composites                  list, ordered by name
GET    /composites/{name}           declaration + segments + quality
PUT    /composites/{name}           replace the declaration → stale
DELETE /composites/{name}           remove + everything derived
POST   /composites/{name}/build     build · 200, not-ready/running → 409
GET    /composites/{name}/bars      Parquet by default, ?format=json
GET    /composites/{name}/quality   the fitness answer (null until built)

The status mapping (statusFor) is the whole error contract on the wire: ErrNotFound → 404; ErrDuplicateName, ErrBuildRunning, ErrNotReady, ErrTransitionInvalid, ErrNotBuilt → 409 (states a Build resolves); ErrInvalidConfig, ErrTimeframeNotMaterialized → 400 (the caller's question to fix); everything else → 500, logged.

On the bars route, what the dataset is travels in headers (X-Composite-State, X-Composite-Mode, X-Timeframe, X-Range-Start/End) before a single body byte — so a stale or research dataset is visibly one even when the body is a Parquet stream. A failure mid-stream truncates and logs; "all the honesty left" once 200 is on the wire.

Also honest: the CLI (agnoforge composite …) is not an adapter of this context — it is an HTTP client of these routes, living in cmd/agnoforge/composite.go, outside the hexagon.

Composition root — who names the concrete types?

One function, serveOn in cmd/agnoforge/serve.go — "the one place in the program where a concrete Store and a concrete Provider are named." Read it downward: it is the whole diagram, in order.

// acquisition first: its store, its provider, its service
store, _ := duckdb.Open(cfg.DBPath)                    // acquisition's schema
provider := binance.New(cfg.BinanceBaseURL, …)
svc := app.New(store, []app.Provider{provider}, …)

// the composite context: same process, same file, own schema (ADR-0005)
compositeStore, _ := compositeduckdb.Open(cfg.DBPath)  // applies composite DDL
compositeSvc := compositeapp.New(compositeStore, acqport.New(svc), …)

// one mux, one port; specific patterns win over the acquisition catch-all
composites := compositehttpapi.New(compositeSvc, logger)
mux.Handle("/composites", composites)
mux.Handle("/composites/", composites)
mux.Handle("/", httpapi.New(svc, logger))

Everything the inner layers left abstract is decided in these lines: which Store (DuckDB, at AGNOFORGE_DB_PATH, default agnoforge.duckdb), which AcquisitionPort (the in-process wrapper — acqport.New(svc) is the only line that knows the two contexts share a process), which inbound surface, on which mux. The dashed red frame around the diagram is this function.

Now derive the rule

Look at every import you have seen: the domain imports stdlib (+ acquisition domain words); the app imports the domain; adapters import the app and the domain; only cmd imports the adapters. The rule was never decreed — it falls out:

domain ← app ← adapters ← cmd        (arrows = "is imported by")

Dependencies point inward. The domain compiles alone; the app compiles against interfaces; every technology sits at the edge, replaceable.

Where does new code go?

Where does "freeze a dataset into an immutable snapshot" go?
The model already reserves room: name@version identity (the @ ban in ParseName) and the copy-on-freeze consequence in ADR-0005. New domain rules in domain/, a use case in app/, new tables in the duckdb adapter.
Where does "a third provider in the middle of the timeline" go?
Refused today by design: the chain is base + catch-up and nothing else (build.go). Changing that is a domain and app decision — assembly and validation already handle N segments (ValidateTransitions iterates), so the change is in how assemble builds the list, not in any adapter.
Where does "serve composites over gRPC" go?
A second inbound adapter beside httpapi, calling the same *app.Service, mounted by the composition root. No inner layer changes.
Where does "run composite in its own service, apart from acquisition" go?
Replace the acqport adapter with an HTTP client (control plane), and replace the Store's source-bar reads with a Parquet/API fetch (data plane). ADR-0005 names exactly these two seams; the domain model does not change.
Where does "a smarter aggregation rule SQL can't express" go?
The duckdb adapter's own ponytail note answers: move the derivation into a Go aggregator over a streamed read of the same rows — "the port signature would not change."

20 · Runtime

Follow one build of btc-research

The happy-but-honest path: a backfill, a catch-up provider, one gap repaired, a priced transition. Click a step or use the arrows — the diagram lights up the hop.

  1. Researcher → RESTPOST /composites/btc-research/build. The handler parses the name and calls svc.Build — nothing else.
  2. Claim & beginclaim(name) takes the one in-memory build slot; State.BeginBuild() moves the dataset to building (a concurrent build gets 409 ErrBuildRunning).
  3. resolveRequestedEnd.Resolve(now): now becomes the last fully closed 1-minute bar. Quality opens against this Resolved End.
  4. ensure (base)Coverage → the missing stretches → StartBackfill + WaitBackfill per stretch, through the port, through acqport, into the acquisition service. A busy backfill is retried; "nothing to acquire" is absorbed.
  5. assemble + catch-upThe base Segment covers what binance supplies. The tail it could not reach is asked of coinbase (the configured catch-up) — tail only, never history the base has. A second Segment abuts the first.
  6. validateValidateTransitions: no overlap (reject_conflict), no hole, same Instrument, same canonical timeframe. A bad seam fails the Build right here, naming which rule broke.
  7. judgePer Segment: Completeness → DetectGaps + RepairGap for what is missing → fresh Completeness; then SourceBars counts what is really there and TransitionDelta prices the seam in SQL, exactly. Survivor gaps land in Quality.
  8. materializeStore.Materialize: one INSERT…SELECT per declared frame (1h, 1d), aggregating the Segments' source bars in SQL — arg_min/arg_max keep every price DECIMAL. A not-ready build hands over the empty Materialization: derived bars are wiped, not written.
  9. SaveBuildOne transaction: the dataset row (ready, research mode judged the flagged gap acceptable), the two Segments, the full Quality — replaced wholesale.
  10. 200 back outThe response is the whole View: declaration + segments + quality. Had strict mode refused, this would be a 409 whose error names every gap, unsupplied stretch and incomplete window — and GET would still show the persisted Quality that explains it.

21 · Runtime

Follow one bars query

The backtester pulls the 1-hour bars of btc-research — no bounds, no format: the defaults are the dataset's own range and Parquet.

  1. Consumer → RESTGET /composites/btc-research/bars?timeframe=1h. An omitted timeframe would mean the 1m timeline; an unknown format is refused, never guessed.
  2. PlanBarsThe handler hands the request to the one method that owns the query's error contract.
  3. Domain rules decideObserved() derives staleness; empty Segments would be 409 ErrNotBuilt; Serves(1h) passes because the declaration materializes 1h (asking for 4h would be 400 naming "1m, 1h, 1d"); QueryRange fills both omitted bounds from the dataset itself.
  4. Headers firstX-Composite-State: ready · X-Composite-Mode: research · X-Timeframe: 1h · X-Range-Start/End — what the dataset is is on the wire before any body byte, whatever happens to the stream after.
  5. ExportBars → StoreThe resolved BarQuery carries the Segments; Derived() is true for 1h, so the adapter reads composite_materialized_bars. A 1m query would instead UNION the Segments' source bars from acquisition's table, clipped, in timeline order.
  6. COPY … TODuckDB writes the Parquet itself — same writer and file layout as acquisition's export. Prices stay DECIMAL(20,8); open_time is epoch milliseconds UTC.
  7. Stream outThe file streams to the consumer, who never learned which provider supplied which period, which gap was repaired, or which of the two read paths answered. That ignorance is the product.
